# TC-PRF-009-11: Input validation + sanitization -> progress 0-100, status enum, notes <=2000 chars, attachments (<=3 files, <=10MB) + XSS/SQLi on notes/comments

## 1. Test Objective
Verify FR-2 field validation and S10 input sanitization for a progress update: progress percentage constrained to 0-100, status constrained to the valid enum, notes max 2000 chars, attachments max 3 files at <=10MB each; and that rich-text notes + comments are sanitized against XSS and SQL injection (stored/rendered safely, server-side validated regardless of client checks).

## 2. Related Requirements
- User Story: US-PRF-009
- Functional Requirements: FR-2 (field constraints), FR-8 (comments)
- Data/Security: S10 input sanitization
- Acceptance Criteria: AC-2

## 3. Preconditions
- Tenant "acme"; employee "Sam Lee" authenticated; goal in the active (open) window.

## 4. Test Data
| Field | Invalid input | Notes |
|-------|---------------|-------|
| Progress | -5 and 101 | outside 0-100 |
| Status | "Frozen" | not in enum |
| Notes | 2001 chars | over max |
| Attachments | 4 files | over max 3 |
| Attachment size | 10MB + 1 byte | over 10MB |
| XSS | `<script>alert(1)</script>` in notes | sanitized |
| SQLi | `'; DROP TABLE goal_progress_updates;--` in notes | parameterized |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Submit an update with progress -5, then 101 | Rejected client + server; the slider clamps and the API returns a validation error -- no record persisted. |
| 2 | Submit an update with status "Frozen" | Rejected -- status must be one of NotStarted/InProgress/Completed/AtRisk/Blocked (FR-7 enum). |
| 3 | Submit notes of 2001 chars | Rejected (max 2000, FR-2); exactly 2000 boundary covered in TC-PRF-009-12. |
| 4 | Attach 4 files | Rejected -- max 3 files (FR-2). |
| 5 | Attach a 10MB+1 file | Rejected -- max 10MB each (FR-2). |
| 6 | Submit notes containing `<script>alert(1)</script>` | Persisted sanitized/escaped; on render it is NOT executed (no alert, no live DOM injection) -- displayed as inert text (S10). |
| 7 | Submit notes / a comment containing the SQLi payload | Treated as literal text via parameterized queries; no SQL executes, the table is intact, the string is stored/escaped. |
| 8 | Verify server-side enforcement | Bypass the client and POST the invalid payloads directly to the API -- all are still rejected/sanitized (defense in depth). |

## 6. Postconditions
- All out-of-range/over-limit inputs are rejected; XSS/SQLi payloads are neutralized; only valid updates persist. No injection executed, no table damaged.
