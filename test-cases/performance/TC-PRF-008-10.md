# TC-PRF-008-10: Immutability -- checkpoint outcomes, status changes, and escalation records form a complete, immutable PIP history for compliance/legal (FR-5)

## 1. Test Objective
Verify FR-5: the system maintains a COMPLETE, IMMUTABLE history of all PIP actions -- every checkpoint outcome, every status change (Draft/Active/Extended/Successfully Completed/Not Met/Cancelled), the acknowledgement event, and the escalation decision. No actor (including HR and the system admin via the normal app surface) can modify or delete a recorded checkpoint outcome, status transition, or escalation record. Each entry carries actor id + server timestamp + tenant_id. This is the compliance/legal evidentiary trail.

## 2. Related Requirements
- User Story: US-PRF-008
- Functional Requirements: FR-5 (immutable history)
- Non-Functional Requirements: NFR-3 (7-year retention -- mechanism), NFR-2 (tenant-scoped audit)
- Acceptance Criteria: AC-3 (checkpoint outcomes), AC-4/AC-5 (status + escalation records)

## 3. Preconditions
- A PIP for Sam Lee exists in acme with: an acknowledgement, at least two recorded checkpoints, an extension, and (for a separate PIP) an escalation decision (from TC-PRF-008-02/03/04/08).
- HR Officer "Nadia Khan" is authenticated in acme.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| History entries | acknowledgement, checkpoints, status changes, escalation | the immutable set (FR-5) |
| Actors | Sam, Dana, Priya, Nadia | each entry attributes its actor |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Open the PIP history/timeline | All entries present in chronological order: acknowledgement, each checkpoint outcome (with evidence/status), each status transition, the escalation decision; each carries actor id + server timestamp (FR-5). |
| 2 | As Nadia, attempt to EDIT a recorded checkpoint outcome (e.g. via a PUT to the checkpoint, or a re-record) | The original outcome is NOT mutated -- either the endpoint is rejected, or a correction is recorded as a NEW appended entry leaving the original intact (append-only); asserted against whatever the implementation documents, but the original is never silently overwritten. |
| 3 | Attempt to DELETE a checkpoint / status-change / escalation record | Rejected -- no actor can delete a history entry through the application surface (FR-5). |
| 4 | Attempt to tamper with the recorded timestamp or actor on any entry | Server-derived timestamp + actor are authoritative; client-supplied overrides are ignored. |
| 5 | After the PIP closes (Successfully Completed / Not Met), re-open the history | The full trail remains intact and read-only post-closure; retained per the tenant retention policy (NFR-3, default 7 years -- retention mechanism asserted at the seam). |
| 6 | Verify tenant scoping of history | Every history entry carries tenant_id = acme; the trail is visible only within acme (NFR-2, cross-tenant in TC-PRF-ISO-029). |

## 6. Postconditions
- The PIP's complete action/checkpoint/status/escalation history is immutable, attributable, tenant-scoped, and retained. No Tenant B data touched.
