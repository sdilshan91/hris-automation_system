# TC-REC-008-06: Expired magic link denies access with a "request new link" prompt; regeneration sends a fresh link only after verifying the email matches an application

## 1. Test Objective
Verify FR-8 / BR-5: when the magic link token has passed its expiry (default 30 days, configurable), accessing the portal is denied and the applicant is shown a "request a new link" prompt. The applicant enters their email; the system verifies the email matches an existing application within the tenant resolved from the subdomain, and only then generates + emails a fresh signed token. If the email does NOT match any application in that tenant, the system returns the SAME neutral "if an application exists, a link has been sent" response (no enumeration) and sends nothing. (Rate limiting on this endpoint is covered in TC-REC-008-11.)

## 2. Related Requirements
- User Story: US-REC-008
- Functional Requirements: FR-8 (link expiry + regenerable via email verification)
- Business Rules: BR-5 (fresh link only after verifying email matches an existing application), BR-4 (tenant from subdomain)
- Data Requirements: S7 (`applicant_portal_token` rotated on regeneration)

## 3. Preconditions
- Tenant "acme"; applicant {acme_applicantId} (applicant@example.com) has an application; an EXPIRED `applicant_portal_token` exists for that email (expires_at in the past).
- A non-existent email (nobody@example.com) has NO application in acme.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Expired link | https://acme.yourhrm.com/portal?token={expiredToken} | expires_at in past |
| Known email | applicant@example.com | has an acme application |
| Unknown email | nobody@example.com | no acme application |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Open the portal via the expired magic link | Access is DENIED; no application data is shown; a clear "your link has expired -- request a new link" prompt with an email field is displayed (FR-8). |
| 2 | Enter the known email applicant@example.com and submit | The system verifies a matching application exists in acme, generates a NEW signed token, rotates/replaces the `applicant_portal_token` row, and emails a fresh magic link; a neutral confirmation is shown (BR-5). |
| 3 | Open the newly emailed link | Access is granted; the dashboard renders as in TC-REC-008-01; the OLD expired token still does not work. |
| 4 | From the prompt, enter the unknown email nobody@example.com and submit | The SAME neutral "if an application exists, a link has been sent" response is shown; NO token is generated and NO email is sent (no account/applicant enumeration) (BR-5). |
| 5 | Verify token freshness | The regenerated token carries a new expiry (now + 30 days default) and is HMAC-signed with tenant_id+email (NFR-4). |

## 6. Postconditions
- Expired token remains invalid; a fresh token exists for the verified email; nothing generated for the unknown email.
