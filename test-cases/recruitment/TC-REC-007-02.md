# TC-REC-007-02: Send to Applicant -> emailed with PDF attachment, status Sent, expiry Hangfire job scheduled (happy path)

## 1. Test Objective
Verify the send flow (AC-2, FR-5/FR-6/FR-7, NFR-4): after a `Draft` offer PDF is generated and previewed (TC-REC-007-01), the recruiter clicks "Send to Applicant". On send the system (a) emails the offer to the applicant's email address with the generated PDF attached via the tenant's notification system (FR-5), (b) changes the offer record status `Draft -> Sent` and sets `sent_at` (FR-6), and (c) schedules the Hangfire job(s) for offer-expiry follow-up: an expiry reminder (configurable days before expiry) and the expiry auto-status-change at `expiry_date` (FR-7). Email delivery is ASYNCHRONOUS via Hangfire/outbox; the API returns success after queuing (NFR-4).

## 2. Related Requirements
- User Story: US-REC-007
- Acceptance Criteria: AC-2
- Functional Requirements: FR-5, FR-6, FR-7
- Non-Functional Requirements: NFR-4 (async email)
- Data Requirements: S7 (`offer.status`, `sent_at`)

## 3. Preconditions
- Tenant "acme" active; recruiter `recruiter@acme` with `Recruitment.Offer.All`.
- A `Draft` offer {acme_offerId} exists for {acme_applicantId} (from TC-REC-007-01) with a tenant-scoped PDF and an expiry_date.
- Notification System (S25) + Hangfire (S28) wired, OR an outbox/log stub is in place (see Conditional note).
- The applicant has a valid email on record.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Offer | {acme_offerId} | status Draft, PDF generated |
| Applicant email | applicant@example.com | recipient |
| Expiry date | generate+7d | drives the Hangfire fire times |
| Reminder lead time | 2 days before expiry | tenant-configurable (FR-7) |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As `recruiter@acme`, `POST /api/v1/recruitment/offers/{acme_offerId}/send` | 200/202; body returns status=`Sent`, sent_at set; the API returns AFTER queuing the email, not after delivery (NFR-4). |
| 2 | Verify status transition | `offer` row status `Draft -> Sent`, `sent_at` populated; version unchanged (FR-6). |
| 3 | Verify email + attachment (async) | An email to applicant@example.com is queued via Hangfire/outbox with the generated offer PDF attached, using the tenant's notification template; if delivery is a LOG-ONLY stub, the outbox/log entry records recipient + attachment storage key (FR-5, NFR-4). |
| 4 | Verify expiry Hangfire jobs scheduled | A reminder job is enqueued to fire at (expiry_date - lead time) and an expiry auto-status job at expiry_date; both carry tenant_id + offer id in their params (FR-7). |
| 5 | Verify applicant stage unchanged on send | Sending does NOT advance the applicant; they remain in "Offer" stage (advancement happens only on acceptance, TC-REC-007-03). |
| 6 | Re-send guard (sanity) | Attempting to "Send" a second time on an already-`Sent` offer does not duplicate the offer; behavior is idempotent or rejected (no duplicate active offer; see BR-2 in TC-REC-007-07). |

## 6. Postconditions
- Offer {acme_offerId} status=`Sent`, sent_at set; offer email + PDF queued; reminder + expiry Hangfire jobs scheduled; applicant still in "Offer" stage.
