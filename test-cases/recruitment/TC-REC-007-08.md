# TC-REC-007-08: Multiple offer versions -> new version supersedes the previous (salary renegotiation) (FR-9)

## 1. Test Objective
Verify offer versioning (FR-9): when offer details change (e.g. salary renegotiated), the recruiter generates a NEW offer version for the same applicant/vacancy; the new version becomes the active offer and the PREVIOUS version is superseded (marked superseded / no longer active), preserving the prior version + PDF for the record. Each version carries an incrementing `version` number and its own tenant-scoped PDF. Versioning is the sanctioned way to satisfy BR-2 (one active offer) while keeping history -- it does NOT delete the prior offer.

## 2. Related Requirements
- User Story: US-REC-007
- Functional Requirements: FR-9 (versions supersede), FR-2/FR-3 (each version gets its own PDF + tenant-scoped path), FR-6 (status)
- Business Rules: BR-2 (single active offer maintained via supersession)
- Assumptions: S10.3 (salary negotiation = generate a new version, no formal workflow)

## 3. Preconditions
- Tenant "acme" active; recruiter `recruiter@acme` with `Recruitment.Offer.All`.
- Applicant {acme_applicantId}/{acme_vacancyId} has an existing offer {acme_offerV1} (version 1, salary 120000), status Sent (or Draft).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| V1 offer | {acme_offerV1} | version 1, salary 120000 |
| V2 salary | 130000 | renegotiated |
| Expected V2 version | 2 | increments |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As `recruiter@acme`, generate a new offer version for {acme_applicantId}/{acme_vacancyId} with salary 130000 (e.g. `POST .../offers?supersede={acme_offerV1}` or the versioning action) | 201; new offer {acme_offerV2} created with version=2, salary 130000, its own pdf_storage_key at the tenant-scoped path; tenant_id from session (FR-9, FR-2, FR-3). |
| 2 | Verify supersession | The new version {acme_offerV2} is the ACTIVE offer; {acme_offerV1} is marked superseded / no longer active (so BR-2 still holds: exactly one active). |
| 3 | Verify V1 retained for record | {acme_offerV1} (and its PDF) is NOT deleted; it remains queryable as a prior version with its original salary 120000. |
| 4 | Verify the new PDF reflects new details | {acme_offerV2}'s PDF substitutes the new salary (130000) and any changed fields; the old PDF still shows 120000. |
| 5 | Verify version chain integrity | The offers for the applicant/vacancy show V1 (superseded) -> V2 (active); version numbers are monotonic; no two active versions. |
| 6 | Send the new version | Sending {acme_offerV2} follows TC-REC-007-02 (status Sent, email + PDF, expiry jobs); the superseded V1's jobs are cancelled. |

## 6. Postconditions
- A second offer version (active) supersedes the first (retained, superseded); BR-2's single-active invariant holds; each version has its own tenant-scoped PDF.
