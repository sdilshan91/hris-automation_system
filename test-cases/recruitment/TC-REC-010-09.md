# TC-REC-010-09: Conversion is atomic -> a failure in ANY step (employee/user/vacancy) rolls back the ENTIRE operation, leaving no orphans (NFR-3, AC-2)

## 1. Test Objective
Verify transactional atomicity (NFR-3, AC-2): the conversion (applicant link update + employee creation + optional user-account creation + vacancy filled_count update) runs as ONE database transaction. If any step fails — e.g. user-account creation hits a duplicate-email conflict, or the vacancy update conflicts — the WHOLE operation is rolled back: no orphan `employee`, no orphan `User`/`UserTenant`, no `filled_count` increment, and the applicant's `converted_to_employee_id` remains null. The HR Officer receives a clear error and can retry. This is the failure-injection complement to the happy path (TC-REC-010-01).

## 2. Related Requirements
- User Story: US-REC-010
- Acceptance Criteria: AC-2 (single coherent creation)
- Non-Functional Requirements: NFR-3 (atomic; rollback on any step failure)
- Cross-story: Authentication (user creation), Core HR (employee creation)

## 3. Preconditions
- Tenant "acme"; setting "Auto-create user accounts on hire" = ENABLED.
- Applicant {acme_applicantId} Hired with Accepted offer; email maya.f@example.com ALREADY exists as a user in acme (forces a duplicate-email conflict during user creation).
- Vacancy {acme_vacancyId} filled_count = 0.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Failure injection | duplicate user email | user-creation step fails mid-transaction |
| Applicant | {acme_applicantId} | not yet converted |
| Vacancy | {acme_vacancyId} | filled_count 0 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Convert {acme_applicantId} (account auto-create enabled; email already taken) | Conversion FAILS with a clear error (e.g. "email already in use / conversion could not be completed") (NFR-3). |
| 2 | Verify no orphan employee | No `employee` row was created for this applicant (the employee insert is rolled back) (NFR-3). |
| 3 | Verify no orphan account | No partial `User`/`UserTenant`/`user_tenant_role` rows remain. |
| 4 | Verify vacancy untouched | Vacancy {acme_vacancyId} filled_count stays 0; status unchanged (FR-7 integrity under rollback). |
| 5 | Verify applicant untouched | {acme_applicantId} `converted_to_employee_id` is still null; stage still Hired; not converted. |
| 6 | Resolve + retry | Fix the conflict (e.g. disable auto-create or free the email) and re-convert -> succeeds cleanly with exactly one employee + one increment (no residue from the failed attempt). |
| 7 | Inject a different mid-step failure (e.g. vacancy update conflict) | Same all-or-nothing outcome: no employee, no account, no increment, applicant unconverted (NFR-3). |

## 6. Postconditions
- After a failed conversion the system state is identical to before the attempt; a subsequent clean conversion creates exactly one of each artifact.
