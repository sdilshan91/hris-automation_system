# TC-REC-007-03: Applicant accepts offer -> status Accepted, applicant advances to "Hired" stage (happy path)

## 1. Test Objective
Verify the acceptance flow (AC-3, FR-6, BR-3): a `Sent` offer is accepted either by the applicant via the candidate portal OR recorded manually by the recruiter. On acceptance the system (a) updates the offer status `Sent -> Accepted` and sets `responded_at`/`response=Accepted`, (b) advances the applicant to the "Hired" pipeline stage (BR-3), writing a stage-history transition row (REC-004 trail), and (c) cancels/short-circuits the pending expiry reminder + auto-status Hangfire jobs so an Accepted offer cannot later flip to Expired. This is the positive branch of AC-3 (decline is TC-REC-007-04).

## 2. Related Requirements
- User Story: US-REC-007
- Acceptance Criteria: AC-3
- Functional Requirements: FR-6, FR-7 (job cancellation)
- Business Rules: BR-3 (acceptance -> Hired advancement)
- Cross-story: US-REC-004 (stage transition + history), US-REC-010 (convert-to-employee seam)

## 3. Preconditions
- Tenant "acme" active; a `Sent` offer {acme_offerId} exists for {acme_applicantId} (from TC-REC-007-02), applicant in "Offer" stage; expiry/reminder jobs scheduled.
- Either the candidate portal accept action OR a recruiter with `Recruitment.Offer.All` to record the response manually.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Offer | {acme_offerId} | status Sent |
| Applicant | {acme_applicantId} | in "Offer" stage |
| Response | Accepted | via portal or recorded by recruiter |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Accept the offer (candidate portal action OR recruiter `POST /api/v1/recruitment/offers/{acme_offerId}/respond` with response=Accepted) | 200; offer status `Sent -> Accepted`, response=Accepted, responded_at set (AC-3, FR-6). |
| 2 | Verify applicant advancement | Applicant {acme_applicantId} advances "Offer" -> "Hired"; a stage-history transition row is recorded (from=Offer, to=Hired, by, timestamp) (BR-3, REC-004 trail). |
| 3 | Verify expiry jobs cancelled | The pending expiry reminder + auto-status Hangfire jobs for {acme_offerId} are cancelled/no-op; the offer cannot later transition to Expired. |
| 4 | Verify convert-to-employee seam (not full workflow) | "Hired" being terminal triggers the convert-to-employee seam (full workflow owned by US-REC-010); only the trigger/hook is asserted here, not employee creation. |
| 5 | Verify single response | Offer status is terminal at Accepted; a subsequent accept/decline on the same offer is rejected (no status flip-flop). |

## 6. Postconditions
- Offer {acme_offerId} status=`Accepted`, responded_at set; applicant in "Hired" stage with a history row; expiry jobs cancelled; convert-to-employee seam triggered.
