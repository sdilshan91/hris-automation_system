# TC-REC-003-02: Drag-and-drop Applied -> Screening persists the stage and records an audit/history entry (happy path)

## 1. Test Objective
Verify AC-2 / FR-3 / BR-5: a recruiter with `Recruitment.Manage.All` drags an applicant card from "Applied" to "Screening"; the UI updates optimistically, the applicant's `pipeline_stage_id` is persisted server-side, the board reflects the move (decremented Applied count, incremented Screening count), and a stage transition record is written to `applicant_stage_history` capturing timestamp, user, from-stage, to-stage (and optional notes).

## 2. Related Requirements
- User Story: US-REC-003
- Acceptance Criteria: AC-2
- Functional Requirements: FR-3
- Business Rules: BR-5
- Data Requirements: S7 (`applicant.pipeline_stage_id`, `applicant_stage_history` audit table)

## 3. Preconditions
- Tenant "acme" is active; a recruiter with `Recruitment.Manage.All` is authenticated.
- Applicant "Jordan Rivera" exists in vacancy "Senior Backend Engineer" at stage "Applied".
- Audit logging module is available for stage-transition tracking (note: assertions on `applicant_stage_history` are the in-module record; the cross-cutting Audit module entry is verified where that module is integrated).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Applicant | Jordan Rivera | Currently at "Applied" |
| From stage | Applied | Source column |
| To stage | Screening | Forward transition (allowed) |
| Actor | recruiter@acme (Recruitment.Manage.All) | Authorized to move |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | On the board, drag Jordan Rivera's card from the Applied column and drop it on the Screening column | A ghost card is shown during drag with a drop-zone highlight; on drop the card appears immediately in Screening (optimistic UI, FR-3). |
| 2 | Observe the stage-move request, e.g. `PATCH /api/v1/recruitment/applications/{applicantId}/stage` with body `{ "toStageId": "<screening>" }` | Request carries `X-Tenant-Subdomain: acme` + bearer. Response is 200 (or 204) within the NFR-2 budget; on failure the optimistic move would revert. |
| 3 | Inspect the response / refresh the board | The applicant is reported at "Screening"; Applied count decremented, Screening count incremented; board total unchanged. |
| 4 | Verify the persisted applicant row | The `applicant` row's `pipeline_stage_id` now references "Screening" (server-side persistence, AC-2). |
| 5 | Verify the stage history record | A new `applicant_stage_history` row exists with: applicant id, from-stage "Applied", to-stage "Screening", actor = recruiter user, a timestamp, tenant_id = acme (BR-5). |
| 6 | Verify the audit log entry | An audit entry is recorded for the stage transition (AC-2) consistent with the cross-cutting Audit module's format. |

## 6. Postconditions
- Jordan Rivera is at "Screening"; exactly one new `applicant_stage_history` row records the Applied->Screening transition.
