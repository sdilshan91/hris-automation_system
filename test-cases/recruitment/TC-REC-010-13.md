# TC-REC-010-13: Performance -> conversion completes <=2s P95 as one atomic transaction; pre-fill form loads <=400ms P95; welcome email async (NFR-1, NFR-4, NFR-5)

## 1. Test Objective
Verify the conversion performance + responsiveness budgets (NFR-1, NFR-4, NFR-5): the atomic conversion transaction (applicant link + employee creation + optional account creation + vacancy update) completes within 2s at P95; the pre-fill form (GET pre-fill payload mapped from application + offer) loads within 400ms at P95; and the welcome email is dispatched ASYNCHRONOUSLY via Hangfire so it does NOT count toward the conversion API latency (NFR-5). Measured under a representative tenant dataset and tenant-scoped.

NOTE: The welcome-email async budget (NFR-5) is asserted as "email send time is excluded from the conversion API latency" — the API returns after enqueuing the job, not after delivery. If Hangfire/S25 delivery is stubbed, assert the enqueue happens before the API response and the response time excludes any send.

## 2. Related Requirements
- User Story: US-REC-010
- Non-Functional Requirements: NFR-1 (conversion <=2s P95, atomic), NFR-4 (pre-fill form <=400ms P95), NFR-5 (welcome email async via Hangfire, non-blocking)

## 3. Preconditions
- Tenant "acme" seeded with a representative volume (e.g. many employees/vacancies) so the count/limit check + employee-number generation run against realistic data.
- Applicant {acme_applicantId} Hired with Accepted offer; load harness able to sample P95 over >=100 conversions/pre-fills.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Pre-fill load target | <=400ms P95 | NFR-4 |
| Conversion target | <=2s P95 | NFR-1 (atomic) |
| Samples | >=100 | for P95 stability |
| Email | async | excluded from API latency (NFR-5) |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Sample the pre-fill form load (GET pre-fill payload) over >=100 requests | P95 <= 400ms (NFR-4). |
| 2 | Sample the conversion (Create Employee) over >=100 atomic conversions | P95 <= 2s including employee + account + vacancy + link writes in ONE transaction (NFR-1). |
| 3 | Verify atomicity is not sacrificed for speed | Each measured conversion is still a single transaction (cross-check TC-REC-010-09's rollback property holds under load). |
| 4 | Verify welcome email is excluded from latency | The conversion API returns after ENQUEUING the welcome-email job; the measured P95 does not include email send time (NFR-5). |
| 5 | Verify tenant scoping under load | All measurements are within acme; the limit/count check and employee-number generation query only acme's data (no cross-tenant scan inflating latency). |

## 6. Postconditions
- No persistent data change beyond the load-test conversions; latency budgets met; email remains out-of-band.
