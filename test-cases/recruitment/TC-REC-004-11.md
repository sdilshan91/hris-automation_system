# TC-REC-004-11: Concurrent stage moves on the same applicant -> optimistic concurrency conflict handled (no lost update, single history row) (NFR-3, story assumption #10.3)

## 1. Test Objective
Verify the optimistic-concurrency assumption (story S10 assumption "EF Core concurrency token on the applicant record"): when two users move the SAME applicant simultaneously, exactly one transition wins and the other receives a concurrency conflict (409) rather than silently overwriting (lost update). The winning move writes one history row; the losing move writes none. This is REC-004-specific (REC-003 did not test concurrent transitions).

## 2. Related Requirements
- User Story: US-REC-004
- Non-Functional Requirements: NFR-3 (atomic write)
- Functional Requirements: FR-2, FR-4
- Assumptions: S10 #10.3 (EF Core concurrency token on applicant)

## 3. Preconditions
- Tenant "acme".
- Applicant "Ira Bose" at "Screening".
- Two authenticated Manage users (User1, User2) holding the same stale row version.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Applicant | Ira Bose ({acme_applicantId}) | At Screening |
| User1 move | Screening -> Interview | Concurrent A |
| User2 move | Screening -> Rejected | Concurrent B |
| Concurrency token | row version / xmin | EF optimistic token |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | User1 and User2 both load Ira at "Screening" (same version) | Both hold the same concurrency token. |
| 2 | User1 commits Screening -> Interview | 200; stage=Interview; token advances; one history row from=Screening, to=Interview. |
| 3 | User2 commits Screening -> Rejected using the now-stale token | 409 Conflict (or equivalent); the move is rejected; NO second history row; the applicant stays at Interview (no lost update). |
| 4 | User2 reloads and retries from the current state | The UI/API surfaces the current stage (Interview); User2 must re-decide from there; a fresh valid move then succeeds. |
| 5 | Verify history integrity | Exactly one history row exists for the contested transition window; no orphaned/duplicate rows; no row pair that implies two simultaneous from=Screening transitions. |
| 6 | DEFERRED note | If the concurrency token is NOT yet wired in this increment, mark this case BLOCKED (do NOT weaken to "last-write-wins"); report the missing token to the caller. |

## 6. Postconditions
- Exactly one concurrent transition succeeded; the conflicting one was rejected with no data corruption.
