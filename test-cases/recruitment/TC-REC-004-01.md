# TC-REC-004-01: Full forward pipeline Applied -> Screening -> Interview -> Offer -> Hired, each transition creating a stage-history record (happy path)

## 1. Test Objective
Verify the primary success flow (AC-1/AC-2/AC-3, FR-2/FR-4): a recruiter advances a single applicant through the complete forward pipeline -- Applied -> Screening -> Interview -> Offer -> Hired -- and EACH of the four transitions updates `applicant.pipeline_stage_id` and writes exactly one `applicant_stage_history` row with from_stage_id, to_stage_id, changed_by, changed_at, notes and tenant_id. This is REC-004's multi-stage end-to-end walk, beyond REC-003's single Applied->Screening drag (TC-REC-003-02).

## 2. Related Requirements
- User Story: US-REC-004
- Acceptance Criteria: AC-1, AC-2, AC-3
- Functional Requirements: FR-2, FR-4
- Data Requirements: S7 (`applicant.pipeline_stage_id`; `applicant_stage_history` row per transition)

## 3. Preconditions
- Tenant "acme" is active; a recruiter with `Recruitment.Manage.All` is authenticated.
- Vacancy "Senior Backend Engineer" is `Open` with headcount > number already hired.
- Applicant "Jordan Rivera" exists at stage "Applied" (not terminal).
- The gate dependencies (interview schedule US-REC-005, scorecard US-REC-006) are either satisfied or treated as soft gates (see TC-REC-004-04); this case assumes gate criteria pass or are overridden so the happy path completes.

| Field | Value | Notes |
|-------|-------|-------|
| Subdomain | acme.yourhrm.com | Active tenant |

| Transition path | Applied->Screening->Interview->Offer->Hired | 4 forward transitions |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | `PATCH /api/v1/recruitment/applications/{acme_applicantId}/stage` -> "Screening" (optional note) | 200; `pipeline_stage_id` = Screening; one new `applicant_stage_history` row: from=Applied, to=Screening, changed_by=recruiter, changed_at set, tenant_id=acme (AC-1, FR-4). |
| 2 | Move "Screening" -> "Interview" | 200; stage = Interview; second history row from=Screening, to=Interview (AC-2). On success the UI prompts to schedule an interview (US-REC-005 seam) -- a prompt, not a blocker, in this happy path. |
| 3 | Move "Interview" -> "Offer" | 200; stage = Offer; third history row from=Interview, to=Offer; the offer generation workflow seam (US-REC-007) is triggered (AC-3). |
| 4 | Move "Offer" -> "Hired" | 200; stage = Hired; fourth history row from=Offer, to=Hired (FR-2). |
| 5 | `GET` the applicant stage timeline | Timeline shows 4 ordered transitions, each with stage name, timestamp, the recruiter who made the change, and notes (matches REC-003 detail timeline AC-3). |
| 6 | Verify persisted history count | Exactly 4 `applicant_stage_history` rows exist for this applicant in acme (one per transition); no duplicate or missing rows. |

## 6. Postconditions
- Applicant "Jordan Rivera" is at terminal stage "Hired"; four immutable stage-history rows record the full path.
