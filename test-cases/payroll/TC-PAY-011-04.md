# TC-PAY-011-04: Duplicate send requires explicit HR confirmation; a re-send after payslips were already sent is blocked until the confirm flag is supplied (negative / FR-7 / BR-5)

## 1. Test Objective
Verify FR-7 and BR-5: the system prevents accidental duplicate sends. If payslips have already been sent for a run, a second "Send Payslips" attempt is NOT executed automatically -- the API requires an explicit confirmation flag (and the UI shows a confirm dialog warning duplicate emails) before re-sending. Without the confirm flag the second invocation is rejected (or returns a "confirmation required" response) and no duplicate emails go out; with the confirm flag the re-send proceeds.

## 2. Related Requirements
- User Story: US-PAY-011
- Acceptance Criteria: AC-1
- Functional Requirements: FR-1, FR-7
- Business Rules: BR-5 (explicit confirmation before re-sending already-sent payslips)

## 3. Preconditions
- Tenant "acme" Finalized run R for May 2026 with 3 employees, all with emails + generated PDFs.
- Payslips have ALREADY been sent once for R (per TC-PAY-011-01): all 3 log rows = Sent.
- HR Officer authenticated with `Payroll.*.All`; SMTP sink captures mail.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Run | R (May 2026), Finalized, already-sent | Sent count = 3 |
| 2nd attempt (no confirm) | confirm=false / omitted | must require confirmation |
| 2nd attempt (with confirm) | confirm=true | re-send proceeds |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Click "Send Payslips" again on the already-sent run R via the UI. | A confirmation dialog appears warning that payslips were already sent and this will re-send duplicate emails; no email is sent yet (FR-7, BR-5). |
| 2 | Forge a direct send request for R WITHOUT the confirmation flag. | API rejects / returns "confirmation required" (e.g. 409); NO new emails sent; no new log rows beyond the existing Sent rows (BR-5). |
| 3 | Verify the SMTP sink after step 2. | No duplicate emails delivered; the original 3 emails remain the only ones. |
| 4 | Submit the send request WITH the confirmation flag (confirm=true). | 202 Accepted; the re-send proceeds; emails are sent again to the 3 employees (FR-7 allows confirmed re-send). |
| 5 | Verify `payslip_email_log`. | The re-send is recorded (status updated / new attempt logged with a fresh sent_at); the run summary reflects the re-send. |

## 6. Postconditions
- An unconfirmed second send is blocked with no duplicate emails; only an explicitly confirmed re-send delivers again.
