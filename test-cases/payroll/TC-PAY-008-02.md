# TC-PAY-008-02: Reject with reason -> Rejected + reason in audit; HR notified; HR adjusts and re-submits (re-submission creates a NEW workflow instance)

## 1. Test Objective
Verify AC-3 / BR-3 / BR-4 / FR-7: the approver identifies discrepancies and clicks "Reject" with a mandatory reason -- run status -> Rejected, HR is notified with the rejection reason, and the reason is stored in the audit trail (`payroll_approval_history`, action=Rejected, comments=reason). HR then makes adjustments, re-calculates back to ReviewPending, and re-submits; the re-submission creates a NEW workflow instance (not a continuation of the rejected one) (BR-3). Status path AwaitingApproval -> Rejected -> ReviewPending is honoured (BR-4).

## 2. Related Requirements
- User Story: US-PAY-008
- Acceptance Criteria: AC-3
- Functional Requirements: FR-1, FR-7, FR-9
- Non-Functional Requirements: NFR-1, NFR-5
- Business Rules: BR-3, BR-4
- Data Requirements: S7 (payroll_approval_history)

## 3. Preconditions
- A June 2026 run is in AwaitingApproval status (submitted by hr1) with workflow instance W1.
- fin1 has `Payroll.Approve`; hr1 has `Payroll.Run`.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Reject reason | "Overtime hours for Dept B look doubled -- please re-verify." | mandatory comment, AC-3 |
| Workflow | W1 (rejected) -> W2 (re-submit) | BR-3 new instance |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As fin1, on the approval review page click "Reject" WITHOUT entering a reason. | Blocked -- the reason/comments field is required for Reject; no status change (AC-3, UI rule). |
| 2 | As fin1, enter the rejection reason and confirm "Reject". | Run status -> Rejected; a `payroll_approval_history` row persists (action=Rejected, actor=fin1, comments=reason, acted_at, ip) (AC-3, FR-7). |
| 3 | Confirm HR is notified. | hr1 receives an in-app + email notification within 30s carrying the rejection reason (AC-3, NFR-1). |
| 4 | As hr1, view the run; confirm the rejection reason is visible. | The rejection reason from fin1 is shown to hr1 (in the timeline + a banner) (AC-3, FR-7). |
| 5 | As hr1, make adjustments / re-calculate so the run returns to ReviewPending. | Status transitions Rejected -> ReviewPending (after corrections) (BR-4); the original W1 instance is closed/terminal. |
| 6 | As hr1, click "Submit for Approval" again. | A NEW workflow instance W2 is created (distinct id from W1); status -> AwaitingApproval; fin1 re-notified; the history retains BOTH the W1 rejection and the W2 submission (BR-3, FR-7). |

## 6. Postconditions
- The rejected attempt (W1) and the re-submission (W2) are both audited; the rejection reason is preserved; the run progresses through a fresh workflow instance.
