# TC-PAY-002-09: Salary revision history captures old/new structure + CTC + changed_by/at + reason (regression)

## 1. Test Objective
Verify BR-3 / FR-4: every salary structure assignment and re-assignment writes a complete salary_revision_history row capturing old_structure, new_structure, old_ctc, new_ctc, effective_from, reason, changed_by, and changed_at. This is a regression guard against history being skipped on edits, overrides, or future-dated changes. History is displayed as a timeline with before/after comparison.

## 2. Related Requirements
- User Story: US-PAY-002
- Acceptance Criteria: AC-2
- Functional Requirements: FR-4
- Business Rules: BR-3
- Non-Functional: NFR-4 (audit before/after)
- Data Requirements: salary_revision_history (S7)

## 3. Preconditions
- Ravi Kumar Active; FT-IN and SR-FT active structures exist.
- HR "Maya Singh" authenticated with `Payroll.*.All`.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Initial | FT-IN, CTC 600,000, eff 2026-07-01 | first assignment (old_structure=null) |
| Revision | SR-FT, CTC 840,000, eff 2026-10-01, reason "Promotion to Senior" | second assignment |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Assign FT-IN (CTC 600,000) to Ravi; confirm. | A salary_revision_history row: old_structure=null, new_structure=FT-IN, old_ctc=null, new_ctc=600000, effective_from=2026-07-01, changed_by=Maya, changed_at set, tenant_id=acme. |
| 2 | Re-assign SR-FT (CTC 840,000, reason "Promotion to Senior", eff 2026-10-01). | A second revision row: old_structure=FT-IN, new_structure=SR-FT, old_ctc=600000, new_ctc=840000, reason="Promotion to Senior", changed_by=Maya, changed_at set. |
| 3 | Open the Compensation tab -> revision timeline. | Timeline shows two entries newest-first, each expandable with a before/after comparison (old vs new structure + CTC). |
| 4 | Apply a component override (HRA custom) on the current assignment. | A revision/audit entry captures the change with before/after values (NFR-4). |
| 5 | Verify changed_by integrity. | changed_by always equals the authenticated user; cannot be spoofed via payload (server-derived). |
| 6 | Verify history is immutable. | Existing revision rows cannot be edited/deleted via the API; only new rows are appended. |

## 6. Postconditions
- Every assignment/change produced a complete, immutable, server-attributed revision-history row.
