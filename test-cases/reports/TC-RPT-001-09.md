# TC-RPT-001-09: Repeat identical request served from Redis cache; Refresh bypasses cache (FR-5, FR-8)

## 1. Test Objective
Verify that a repeated report request with identical parameters is served from the Redis cache
(keyed `t:{tenantId}:report:{name}:{paramsHash}`, TTL 5-15 min) rather than recomputed, and that
the "Refresh" option bypasses the cache and regenerates (FR-8). Also verify cache keys are
parameter-sensitive (different filters -> different key) and tenant-scoped.

> PLATFORM NOTE / CONDITIONAL: FR-5 specifies Redis. If Redis is not wired in the test
> environment (deferred infra on the dev box, as in prior modules), this TC is CONDITIONAL:
> assert instead that (a) repeated identical requests return identical results, (b) Refresh
> re-queries the source, and (c) the cache KEY SHAPE includes `t:{tenantId}` and a hash of the
> exact filter set when caching IS enabled. Do NOT relax the NFR-1 latency threshold to compensate
> for an absent cache — record indicative numbers.

## 2. Related Requirements
- User Story: US-RPT-001
- Acceptance Criteria: AC-2
- Functional Requirements: FR-5 (Redis cache, tenant+params keyed), FR-8 (Refresh bypass), FR-7
- Dependencies: Redis

## 3. Preconditions
- Tenant A active; `hr1` authenticated with `Reports.View.All`.
- Redis available (else run CONDITIONAL per the note above).
- A report exists that is non-trivial to compute (so cache vs compute timing is distinguishable).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| report_type | headcount_summary | |
| params set 1 | dept=Engineering, current month | -> cache key K1 |
| params set 2 | dept=Sales, current month | -> different cache key K2 |
| cache key shape | t:{tenantId}:report:headcount_summary:{hash(params)} | FR-5 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Generate the report with params set 1 (cold) | Result computed from source; a Redis entry is created at key K1 (TTL 5-15 min); record latency T_cold |
| 2 | Re-generate with identical params set 1 | Served from cache (cache hit at K1); result identical to step 1; latency T_warm < T_cold |
| 3 | Inspect the Redis key used | Key matches `t:{tenantId}:report:headcount_summary:{paramsHash}` and is scoped to Tenant A's id |
| 4 | Generate with params set 2 (different department) | Distinct cache key K2 created; not a hit on K1 — confirms params-sensitivity |
| 5 | Click "Refresh" on params set 1 | Cache BYPASSED; report recomputed from source (FR-8); entry at K1 refreshed/overwritten |
| 6 | Mutate underlying data (add an active employee), then request params set 1 WITHOUT Refresh within TTL | Stale cached value returned (expected cache behavior) |
| 7 | Click Refresh after the mutation | New value reflects the added employee — confirms Refresh sees fresh data |

## 6. Postconditions
- Cache hit/miss and Refresh-bypass behavior verified; key is tenant- and params-scoped.
