# TC-RPT-005-11: Dashboard load <=2s P95 (NFR-1); per-widget <500ms P95 (NFR-2); Redis cache TTL 2-5min + refresh bypass (FR-4); auto-refresh 5min + manual (FR-9)

## 1. Test Objective
Verify dashboard performance and caching: total dashboard load is <=2s P95 (NFR-1), each widget's data
completes within 500ms P95 (NFR-2), widget data is cached in Redis with TTL 2-5 min keyed
`t:{tenantId}:dashboard:{role}:{userId}:{widgetKey}` (FR-4), `refresh=true` bypasses the cache, and the UI
auto-refreshes every 5 minutes with a manual Refresh available (FR-9). Redis is DEFERRED dev-box infra:
the cache steps are CONDITIONAL on Redis being wired; thresholds are NEVER relaxed to compensate for an
absent cache. Validates AC-1, FR-4, FR-9, NFR-1, NFR-2, NFR-6.

## 2. Related Requirements
- User Story: US-RPT-005
- Acceptance Criteria: AC-1
- Functional Requirements: FR-4 (Redis cache TTL 2-5min, tenant+role+user+widgetKey), FR-9 (auto-refresh 5min + manual)
- Non-Functional: NFR-1 (dashboard load <=2s P95), NFR-2 (widget <500ms P95), NFR-6 (lazy render visible widgets)

## 3. Preconditions
- Tenant A active; HR Officer `hr1` authenticated.
- A perf-representative dataset (realistic per-module volumes). On a dev box, record indicative numbers and DO NOT relax thresholds.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| dashboard load budget | <= 2000 ms P95 | NFR-1 |
| per-widget budget | < 500 ms P95 | NFR-2 |
| cache key | t:{tenantId}:dashboard:{role}:{userId}:{widgetKey} | FR-4 |
| cache TTL | 120-300 s (2-5 min) | FR-4 |
| auto-refresh interval | 300 s (5 min) | FR-9 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Load the dashboard repeatedly; measure full-load latency | P95 <= 2s for all visible widgets (NFR-1) |
| 2 | Measure each widget's data fetch latency | P95 < 500ms per widget (NFR-2) |
| 3 | (Redis-conditional) Load twice within TTL; inspect cache | second load served from Redis under key `t:{tenantId}:dashboard:hr:{hr1Id}:{widgetKey}`; TTL within 2-5 min (FR-4) |
| 4 | (Redis-conditional) Confirm key derivation | the key includes tenant + role + userId + widgetKey -- per-user, per-role, per-tenant (FR-4) |
| 5 | `GET /api/v1/dashboard/widgets?refresh=true` | cache is BYPASSED; data re-composed from per-module services; cache entry refreshed (FR-4) |
| 6 | If Redis is NOT wired (deferred) | assert identical results on immediate repeat + that `refresh=true` re-queries + the intended key shape is documented; thresholds in steps 1-2 are NOT relaxed |
| 7 | Leave the dashboard open ~5 min | the UI auto-refreshes data without a full page reload (FR-9) |
| 8 | Click the manual "Refresh" button | data re-fetched on demand (equivalent to `refresh=true`) (FR-9) |
| 9 | Confirm lazy rendering | only visible widgets render their charts (off-screen charts deferred) (NFR-6) |

## 6. Postconditions
- Latency budgets met; cache (when wired) tenant+role+user scoped with correct TTL; refresh bypass + auto/manual refresh verified.
