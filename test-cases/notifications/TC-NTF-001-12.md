# TC-NTF-001-12: Performance — end-to-end delivery latency <= 2s (NFR-1)

## 1. Test Objective
Verify real-time delivery latency from event creation (notification persisted/published) to
client display is <= 2 seconds at P95 under representative load, via the SignalR + Redis
backplane path. Also exercises FR-10 multi-instance backplane fan-out.

## 2. Related Requirements
- User Story: US-NTF-001
- Acceptance Criteria: AC-2
- Functional Requirements: FR-4 (real-time push), FR-10 (Redis backplane)
- Non-Functional: NFR-1 (<= 2s delivery), NFR-3 (>= 5,000 concurrent connections/instance)

## 3. Preconditions
- A performance-representative environment with the Redis backplane and (ideally) >= 2 API instances.
- A population of connected clients across Tenant A (target several thousand to approach NFR-3).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| latency SLA | <= 2s end-to-end | NFR-1 |
| measurement percentile | P95 | |
| concurrent connections | up to 5,000/instance | NFR-3 target |
| sample size | >= 1,000 notifications | for stable percentile |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Establish the connected-client population | Connections stable; no mass drops |
| 2 | Emit >= 1,000 notifications, timestamping creation and client receipt | Latency captured per notification |
| 3 | Compute the latency distribution | P95 <= 2s end-to-end (creation -> client display) |
| 4 | Emit a notification on API instance 1 to a client connected to instance 2 | Delivered via Redis backplane within SLA (cross-instance fan-out works) |
| 5 | Hold ~5,000 concurrent connections on one instance and emit a burst | Hub stays healthy; latency SLA still met (NFR-3) |
| 6 | Record indicative numbers if run on a dev box | Do NOT relax the 2s threshold; flag environment limitations |

## 6. Postconditions
- Delivery latency characterized against the 2s SLA; backplane fan-out verified.
