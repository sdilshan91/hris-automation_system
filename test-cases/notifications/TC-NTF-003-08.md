# TC-NTF-003-08: Preference change invalidates cache; next dispatch reflects the change (Redis-deferred conditional)

## 1. Test Objective
Verify that changing a user's notification preference invalidates the cached preference lookup so the
NEXT notification dispatch reflects the new preference (no stale cached decision). Where the Redis
preference cache is wired, assert key invalidation; where Redis is not yet provisioned, assert the
equivalent always-fresh, tenant+user-scoped DB lookup so behavior is correct regardless.

## 2. Related Requirements
- User Story: US-NTF-003
- Acceptance Criteria: AC-2 (preference applied to future events)
- Functional Requirements: FR-6 (preferences applied at dispatch time)
- Non-Functional: NFR-3 (preference lookup cached in Redis, TTL 5 min, to avoid per-notification DB queries)
- Business Rules: BR-6 (changes take effect immediately for future notifications)

## 3. Preconditions
- Employee `emp1` (Tenant A) currently has Email ENABLED for "Leave Updates".
- The Notification Dispatcher consults the preference lookup (cached if Redis is provisioned).
- NOTE: Redis preference caching (NFR-3) is a deferred infrastructure item on the current dev box;
  this TC is CONDITIONAL on Redis being wired -- otherwise verify the equivalent fresh DB lookup.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| cache key (if wired) | notif:prefs:{tenant_id}:{user_id} | tenant + user scoped |
| TTL | 5 minutes | NFR-3 |
| before change | Leave Updates Email = true | |
| after change | Leave Updates Email = false | |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Trigger a leave event so the Dispatcher loads `emp1`'s prefs | Email sent (Email currently enabled); if Redis wired, the preference entry is now cached under a tenant+user-scoped key |
| 2 | As `emp1`, disable Email for "Leave Updates" and save | Auto-save persists channel_email=false; the cached preference entry is invalidated/evicted (if Redis wired) |
| 3 | Trigger a second leave event | NEXT dispatch reflects the change: NO email sent (in-app only) -- not a stale cached "email enabled" decision (FR-6, BR-6) |
| 4 | (If Redis wired) inspect the cache | Stale entry was removed/refreshed; new entry (if repopulated) reflects channel_email=false; key is tenant+user-scoped |
| 5 | (If Redis NOT provisioned) confirm path | Dispatcher reads fresh from DB each time; the change is honored on the very next event; CONDITIONAL items recorded as deferred, not as a coverage gap |

## 6. Postconditions
- No stale preference decision survives a change; the next dispatch honors the latest preference.
