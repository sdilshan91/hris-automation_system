# TC-NTF-002-02: No tenant override -> system default template used (fallback)

## 1. Test Objective
Verify that when a tenant has NOT customized an event template, the platform falls back to the
system default template for that event — and never sends an email without a template.

## 2. Related Requirements
- User Story: US-NTF-002
- Acceptance Criteria: AC-1 (list shows "Default" status)
- Functional Requirements: FR-6 (fall back to system default)
- Business Rules: BR-2 (every event has at least a system default; never send without a template)

## 3. Preconditions
- Tenant B is active; Tenant B has created NO override for `leave_approved` (uses default).
- System default "Leave Approved" template exists (tenant_id = null).
- Employee `empB` belongs to Tenant B and has a pending leave request.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| event_key | leave_approved | |
| Tenant B override | none | |
| default subject | "Your leave request has been approved" | system default |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As Tenant Admin B, open the template list | "Leave Approved" shows status badge "Default" (not "Custom") |
| 2 | As a manager, approve `empB`'s leave request | Approval persists; a `leave_approved` email is enqueued |
| 3 | Inspect the delivered/captured email | Email is rendered from the SYSTEM DEFAULT template; placeholders resolved with Tenant B / empB data |
| 4 | Compare against Tenant A's custom subject (TC-NTF-002-01) | Tenant B's email subject is the default, NOT Tenant A's custom subject — no cross-tenant template bleed |
| 5 | Confirm the email was actually sent | Exactly one email dispatched; BR-2 honoured (a template always exists) |

## 6. Postconditions
- Tenant B remains on the system default; one default-rendered email delivered.
