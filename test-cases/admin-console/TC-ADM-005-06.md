# TC-ADM-005-06: Plan user-limit enforced at invite time (5 succeed, 6th rejected)

## 1. Test Objective
Verify AC-2 / BR-5 / Test-Hint "Plan limit enforcement": the plan user limit (`Tenant.MaxEmployees`) is enforced at INVITATION time. With `MaxEmployees = 5`, the first invites that bring the count to 5 succeed; the invite that would exceed 5 is rejected with "User limit reached for your plan." Existing-over-limit users (after a downgrade) remain active, but no new invitation is allowed.

## 2. Related Requirements
- User Story: US-ADM-005
- Acceptance Criteria: AC-2
- Business Rules: BR-5
- Test Hints: Plan limit enforcement

## 3. Preconditions
- Tenant Admin "Dana" authenticated on Acme; `Tenant.MaxEmployees = 5`.
- Acme currently has 4 counted memberships (active + invited count toward the limit per the implemented rule).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| MaxEmployees | 5 | plan limit |
| existing count | 4 | active/invited |
| invite #5 | user5@acme.io | brings count to 5 — allowed |
| invite #6 | user6@acme.io | would exceed — rejected |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Invite user5@acme.io | 201/200; membership count reaches 5 (at the limit). |
| 2 | Invite user6@acme.io | Rejected (409/422) with message "User limit reached for your plan." |
| 3 | Query `user_tenant`/`user_invitation` for user6 | No membership and no invitation row was created. |
| 4 | (Downgrade scenario) Set MaxEmployees to 3 while 5 users exist; attempt any new invite | Rejected; existing 5 memberships remain active/unchanged — over-limit existing users are NOT deactivated (BR-5). |
| 5 | Query `audit_log` | The rejected invite is logged as a denied action (actor, reason). |

## 6. Postconditions
- Acme has exactly 5 memberships; no invite exceeded the plan limit; the limit is checked at invite time, not login.
