# TC-ADM-001-12: Provisioning is idempotent — retry after partial failure never duplicates

## 1. Test Objective
Verify NFR-2 and the "partial failure" Test Hint: if a provisioning attempt partially fails (e.g. the welcome-email step fails after the transactional create), retrying with the SAME subdomain either completes the operation or returns a clear error — it never creates duplicate tenants, users, user_tenant rows, lifecycle events, or audit "created" entries.

## 2. Related Requirements
- User Story: US-ADM-001
- Non-Functional: NFR-2
- Functional Requirements: FR-3 (atomic transactional create), FR-4 (welcome email)
- Test Hints: partial failure (email service down), concurrent provisioning

## 3. Preconditions
- System Admin authenticated at `admin.yourhrm.com` with the `SystemAdmin` role.
- The ability to inject a failure into the email-dispatch step (e.g. point SMTP at an unreachable host).
- No tenant with subdomain `resilient` exists.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Subdomain | resilient | unique at start |
| Owner email | owner@resilient.com | new user |
| Plan / region | valid | |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Inject an email-service failure, then submit the `resilient` provisioning request | Per FR-3 the transactional create (tenant/user/user_tenant/seed/lifecycle) commits atomically OR rolls back atomically. Record which: if the tenant is created, the email is left retriable; if the whole thing rolls back, no rows exist. Either way the response communicates the outcome clearly. |
| 2 | Restore the email service and RETRY the same `resilient` payload | The retry does NOT create a second tenant: if step 1 committed the tenant, the retry completes the outstanding email dispatch (or no-ops) and returns success/clear status; if step 1 rolled back, the retry creates exactly one tenant. |
| 3 | Count rows after the retry | Exactly ONE `tenant` row for `resilient`, ONE owner `users` row, ONE `user_tenant`/`TenantOwner`, ONE `tenant_lifecycle_event` `created`, and no duplicate `system_audit_log` "created" entries. Welcome email dispatched exactly once (no double-send). |
| 4 | Submit two `resilient` provisions concurrently (race on subdomain uniqueness) | Exactly one succeeds; the other is rejected with "Subdomain is unavailable" (BR-2 uniqueness holds under concurrency); no duplicate rows. |

## 6. Postconditions
- After any combination of partial failure + retry + concurrent submit, exactly one consistent `resilient` tenant exists with no duplicates.
