# TC-ADM-003-04: Read-only enforcement — SystemSupport impersonation is always read-only (write -> 403)

## 1. Test Objective
Verify AC-6 / BR-1: a user with the `SystemSupport` role may initiate impersonation, but the session is ALWAYS read-only regardless of tenant status. The impersonation JWT carries `imp_readonly=true`; write Commands return 403 ("Support impersonation is read-only"); reads succeed.

## 2. Related Requirements
- User Story: US-ADM-003
- Acceptance Criteria: AC-6
- Functional Requirements: FR-3
- Business Rules: BR-1
- Test Hints: SystemSupport read-only

## 3. Preconditions
- Initiator "Sam Support" has the `SystemSupport` role.
- Target tenant "Acme" is `active` (NOT suspended) — proves read-only comes from the role, not the tenant status.
- Target user has active membership in Acme.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Initiator role | SystemSupport | always read-only |
| target tenant | Acme (active) | not suspended |
| write endpoint | a tenant write Command | should 403 |
| read endpoint | a tenant read Query | should 200 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As Sam (SystemSupport), start impersonation against the Acme target user | 200; impersonation JWT has `imp_readonly=true` even though Acme is active (read-only driven by SystemSupport role). |
| 2 | With the token, call a read Query | 200; reads permitted. |
| 3 | With the token, call a write Command | 403 with "Support impersonation is read-only."; no mutation. |
| 4 | Confirm the session row records the SystemSupport initiator and read-only mode | `impersonation_sessions` impersonator = Sam; read-only enforced by the pipeline behavior. |

## 6. Postconditions
- SystemSupport impersonation is read-only by role; writes blocked server-side.
