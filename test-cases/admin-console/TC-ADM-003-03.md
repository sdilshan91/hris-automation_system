# TC-ADM-003-03: Read-only enforcement — impersonation in a SUSPENDED tenant blocks writes (403), allows reads

## 1. Test Objective
Verify AC-5 / BR-1: when a System Admin impersonates a user in a `Suspended` tenant, the session is marked read-only at start (`imp_readonly=true`). A write Command during that session is rejected with 403 by the read-only MediatR pipeline behavior, while read Queries succeed.

## 2. Related Requirements
- User Story: US-ADM-003
- Acceptance Criteria: AC-5
- Functional Requirements: FR-3
- Business Rules: BR-1
- Test Hints: Read-only for suspended tenants

## 3. Preconditions
- Target tenant "Beta" has `status = Suspended`; target user has active membership.
- Initiator is a full `SystemAdmin`.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| target tenant | Beta (Suspended) | drives read-only |
| read endpoint | `GET /api/v1/employees` (tenant-scoped) | should succeed |
| write endpoint | `POST /api/v1/employees` (a write Command) | should 403 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Start impersonation against the Beta target user | 200; impersonation JWT has `imp_readonly=true` because the tenant is Suspended (AC-5/BR-1). Session row `status=Active`. |
| 2 | With the impersonation token, call a read Query (e.g. list employees) | 200; data returned — reads are permitted. |
| 3 | With the impersonation token, call any write Command (create/update) | 403; message indicates read-only impersonation; no data is mutated. |
| 4 | Verify no audit "action" row for the blocked write reflects a successful mutation | The write is denied at the pipeline behavior before persistence; tenant data unchanged. |

## 6. Postconditions
- Suspended-tenant impersonation is read-only; reads work, writes are blocked at the server.
