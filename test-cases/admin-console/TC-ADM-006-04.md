# TC-ADM-006-04: Branding — file with wrong magic bytes (spoofed .png) rejected server-side

## 1. Test Objective
Verify NFR-2: branding validation is by MAGIC BYTES, not file extension. A file named `logo.png` whose actual content is NOT a PNG (e.g. a renamed text/HTML/EXE payload, or a JPEG/GIF disguised as `.png`) is rejected with 400, nothing is stored, and `branding.logo_url` is unchanged. This guards against content-type spoofing and stored-XSS via a polyglot upload.

## 2. Related Requirements
- User Story: US-ADM-006
- Acceptance Criteria: AC-2
- Functional Requirements: FR-2
- Non-Functional: NFR-2 (server-side magic-byte validation)

## 3. Preconditions
- Tenant Admin "Dana" authenticated at `acme.yourhrm.com`; a known-good `branding.logo_url` baseline exists.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| spoofed file | `logo.png` containing `<html>...` / EXE bytes | wrong magic bytes |
| disguised image | JPEG bytes named `.png` | type mismatch |
| declared content-type | `image/png` | header lies; server must not trust it |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Upload `logo.png` whose bytes are HTML/text, content-type `image/png` | 400; rejected (magic bytes ≠ PNG/SVG); no file stored. |
| 2 | Upload JPEG bytes renamed `logo.png` | 400; rejected (magic bytes are JPEG, not an allowed logo type). |
| 3 | Upload a file with a double extension `logo.png.svg` containing script | 400 or sanitized; no executable/script content served from the branding path. |
| 4 | `GET` branding settings | `branding.logo_url` unchanged from baseline. |
| 5 | Inspect storage `{tenantId}/branding/` | No new/partial file written for the rejected uploads. |

## 6. Postconditions
- No spoofed file persisted; branding URL at baseline; rejection (no false accept).
