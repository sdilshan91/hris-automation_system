# TC-ADM-009-16: [DEFERRED/CONDITIONAL] Downgrade does not retroactively block existing data; new creations blocked when over limit

## 1. Test Objective
Verify BR-4 + the downward path of the "Edit plan propagation" Test Hint: lowering a plan limit does NOT retroactively affect existing tenant data. Example: `max_employees` reduced 200 -> 100 while a tenant already has 150 employees — the tenant keeps its 150 employees but cannot ADD new ones until under the new limit.

DEFERRED / CONDITIONAL — status: blocked. This behavior depends on EACH module performing a create-time limit check against the live plan/derived limit. The retroactive-preservation half (existing data untouched) is inherent (no module deletes data on a plan edit). The new-creation-block half is only enforced where a module actually checks the limit at create time. As of US-ADM-009, the verified create-time limit check is the EMPLOYEE limit (`Tenant.MaxEmployees`, exercised upward in TC-ADM-009-07 and by Recruitment/Core HR). Other limit keys (storage, API calls, email sends, custom roles, custom fields, workflows, integrations, concurrent sessions) do not all have create-time enforcement yet, so their over-limit blocking is conditional on the owning module adding the check.

## 2. Related Requirements
- User Story: US-ADM-009
- Business Rules: BR-4 (lowering a limit does not retroactively block existing data; new creations blocked when over limit)
- Test Hints (Edit plan propagation — downward)

## 3. Preconditions
- System Admin "Pat" authenticated; plan `growth` max_employees=200; tenant "Acme" on `growth` with 150 active employees.
