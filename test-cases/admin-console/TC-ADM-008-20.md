# TC-ADM-008-20: [DEFERRED] PII-read events logged and visible in the audit log

## 1. Test Objective
Verify BR-6: reads of sensitive employee PII fields (e.g. national ID, bank account) are LOGGED as audit events and visible in the audit log — so a Tenant Admin can see who accessed sensitive data.

DEFERRED — status: blocked. The audit log infrastructure captures all WRITES (via the SaveChanges interceptor) and any events that modules already emit, but NO new PII-READ instrumentation was added for this story. PII-read rows appear in the audit log ONLY IF the originating module already emits them today; no read-side capture was built. (Story §10 also states reads of non-sensitive fields are intentionally not captured.)

## 2. Related Requirements
- User Story: US-ADM-008
- Business Rules: BR-6 (PII access events logged + visible)
- Functional Requirements: FR-1/FR-2 (such rows would surface through the normal list/detail once emitted)

## 3. Preconditions
- (Deferred prerequisite) The relevant module emits a PII-read audit event when a national ID / bank account is read.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| read action | e.g. "Employee.PiiRead" | only if a module emits it |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | (When implemented) Read an employee's national ID / bank account via a module that emits a PII-read event | A PII-read audit row is written for the current tenant. |
| 2 | View the audit log | The PII-read event is visible, filterable by action/resource (and the sensitive value is masked per FR-4). |
| 3 | Until implemented | Expected behavior: "Not available — no new PII-read instrumentation added; PII-read rows surface only if a module already emits them. The audit list/detail/masking machinery (TC-ADM-008-01/-09/-10) will display them correctly once emitted." |

## 6. Postconditions
- Deferred; no new read-side capture today.
