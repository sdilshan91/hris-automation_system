# TC-ADM-003-15: [DEFERRED] Tenant-admin notification DELIVERY (email + in-app)

## 1. Test Objective
Verify AC-4 / FR-5: when an impersonation session starts, the tenant's Tenant Admin(s) receive a notification via BOTH email and in-app channels using the `impersonation_started` template, containing impersonator name, target user, timestamp, reason, and session reference.

## 2. Related Requirements
- User Story: US-ADM-003
- Acceptance Criteria: AC-4
- Functional Requirements: FR-5
- Test Hints: Tenant admin notification

## 3. Status — DEFERRED / BLOCKED
**Blocked: delivery is a log-only seam today.** The impersonation-start notification is implemented as a **log-only dispatch seam** — the start flow records that a notification SHOULD be sent (with the full payload: impersonator, target, timestamp, reason, session id), but real email + in-app DELIVERY is deferred to the Notification module (US-NTF). The DISPATCH/enqueue assertion is covered run-green in TC-ADM-003-01 (step 7); only the actual multi-channel delivery is deferred here.

**Expected behavior once US-NTF lands:** an email is delivered to each Acme Tenant Admin AND an in-app notification appears, both rendered from the `impersonation_started` template with the verbatim reason and session reference.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| template | impersonation_started | system notification template |
| channels | email + in-app | both required by FR-5 |
| payload | impersonator, target_user, timestamp, reason, session_id | per AC-4 |

## 5. Test Steps (to enable once US-NTF delivery lands)
| Step | Action | Expected Result |

| 4 | (Run-green today) Assert the dispatch seam fired | See TC-ADM-003-01 step 7 — the notification payload is recorded/enqueued even though delivery is deferred. |
