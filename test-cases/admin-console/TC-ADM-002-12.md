# TC-ADM-002-12: Dashboard loads within 2.5s (P95) with 100+ tenants

## 1. Test Objective
Verify NFR-1: the monitoring dashboard (initial overview fetch + render) completes within 2.5 seconds at P95 with a realistic platform of 100+ tenants. Monitoring queries must not degrade production DB performance (NFR-3) — assert via pre-aggregation/read-path, not per-tenant N+1 scans.

## 2. Related Requirements
- User Story: US-ADM-002
- Non-Functional Requirements: NFR-1, NFR-3
- Acceptance Criteria: AC-1 (load performance)
- Test Hints: dashboard loads within 2.5s with 100+ tenants

## 3. Preconditions
- Performance-representative environment seeded with >= 100 tenants and a realistic employee/user distribution.
- System Admin authenticated; a latency-capture tool available.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Tenant count | 120 | >= 100 |
| Iterations | >= 50 dashboard loads | for P95 |
| SLA | P95 <= 2.5s end-to-end | NFR-1 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Run >= 50 cold/warm dashboard loads against the 120-tenant dataset | Capture end-to-end load time (request + render) per iteration. |
| 2 | Compute P95 of the load times | P95 <= 2.5s (NFR-1). |
| 3 | Inspect the overview query plan / count | The overview is served via aggregate/pre-aggregated queries (bounded number of queries), not one query per tenant; no full-table N+1 scan (NFR-3). |
| 4 | Observe production DB load during the run | Monitoring queries do not spike contention on tenant-facing tables beyond the agreed budget (NFR-3). |
| 5 | (Note) SignalR push latency (NFR-2) | NOT tested — push is deferred; refresh is polling (see TC-ADM-002-07). |

## 6. Postconditions
- Dashboard meets the 2.5s P95 budget at 100+ tenants without harming DB performance.
