# TC-ONB-002-11: Checklist assignment API within 1000 ms P95 (NFR-1)

## 1. Test Objective
Verify NFR-1: the checklist-assignment API responds within 1000 ms at the 95th percentile under representative load, including creation of all task instances, responsible-party resolution, and writing notification outbox rows in the same transaction.

## 2. Related Requirements
- User Story: US-ONB-002
- Acceptance Criteria: AC-2
- Non-Functional Requirements: NFR-1, NFR-3
- Note: requires a performance-representative environment (warm app + representative DB). On a non-representative dev box, record observed numbers and flag as indicative only — do NOT relax the threshold.

## 3. Preconditions
- A performance-representative environment with the API warmed (JIT/connection pool primed).
- Tenant `acme` pre-seeded with employees and an active template containing a representative task count (e.g. 8-12 tasks).
- A test harness (e.g. k6/JMeter) issuing concurrent `POST /api/v1/onboarding/assignments` requests (distinct employees, no active checklist).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Payload | employee_id + template_id (8-12 tasks) | representative size |
| Concurrency | sustained representative RPS | per harness config |
| Sample size | >= 200 successful assignments | for a stable P95 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Warm the API, then run the assignment scenario at target concurrency | All requests return 201 (distinct employees). |
| 2 | Record server-side latency per request | Capture full distribution (P50/P95/P99), including task-instance creation, party resolution, and outbox writes. |
| 3 | Compute P95 | P95 of assignment latency <= 1000 ms (NFR-1). |
| 4 | Inspect outliers | P99 reviewed; any breach is reported with the trace, not silenced. |

## 6. Postconditions
- A latency report (P50/P95/P99) recorded; P95 meets the 1000 ms SLA or the breach is reported to the caller.
