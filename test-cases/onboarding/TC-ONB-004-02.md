# TC-ONB-004-02: Bulk issuance — 3 assets in one submission persisted in a SINGLE transaction (atomic)

## 1. Test Objective
Verify FR-5 and NFR-5: three assets submitted in one issuance form are persisted atomically — all asset status updates and employee linkages commit in a single database transaction. If any one asset fails mid-batch, the entire submission rolls back (no partial state).

## 2. Related Requirements
- User Story: US-ONB-004
- Acceptance Criteria: AC-1, AC-2
- Functional Requirements: FR-5
- Non-Functional Requirements: NFR-5 (atomic, single transaction)

## 3. Preconditions
- HR Officer authenticated in tenant `acme` with `Onboarding.Manage`.
- Employee E201 exists; three assets (LAP-010, PHN-010, BDG-010) are in "available" status.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| employee_id | E201 | |
| assets | [LAP-010 Laptop, PHN-010 Phone, BDG-010 Access Badge] | all available, condition New, issue_date today |
| fault injection (step 4) | one asset made invalid mid-batch | to prove rollback |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Submit all 3 assets in one issuance request for E201 | 200/201; success toast "3 asset(s) issued to [E201 name]". |
| 2 | Inspect the register | All three (LAP-010, PHN-010, BDG-010) status="assigned", assigned_employee_id=E201 (FR-5). |
| 3 | Inspect the persistence | All 3 issuance rows share the same created timestamp/transaction; tenant_id=T-acme on each (NFR-5). |
| 4 | Repeat with a batch where the 3rd asset is already assigned to another employee (forces failure) | Whole submission rejected; NONE of the 3 are assigned — the first two are NOT left in "assigned" state (atomic rollback, NFR-5). |
| 5 | Re-inspect the register after the failed batch | LAP-010/PHN-010 (or the valid two) remain "available"; no orphaned partial linkage. |

## 6. Postconditions
- Successful batch: all 3 assigned in one transaction. Failed batch: full rollback, register unchanged.
