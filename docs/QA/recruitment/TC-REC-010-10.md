# TC-REC-010-10: Subscription employee limit blocks conversion -> at/over MaxEmployees the conversion is blocked with an upgrade message; null limit = unlimited (BR-3)

## 1. Test Objective
Verify the subscription-limit guard (BR-3, story precondition): if creating the employee would push the tenant's active employee count OVER its subscription plan's `MaxEmployees`, the conversion is blocked BEFORE any write, with a clear "upgrade your plan" message; no employee, account, link, or filled_count increment occurs. Also asserts the boundaries: exactly AT the limit (count == MaxEmployees) blocks, count == MaxEmployees - 1 succeeds (fills the last allowed seat), and `MaxEmployees = null` means UNLIMITED (never blocks).

NOTE: `MaxEmployees` is a nullable field on the Tenant entity (null = unlimited; current placeholder until a proper Subscription/Plan entity exists). This case tests against that field as-is; if/when plan enforcement moves to a Subscription entity, re-point the limit source — the BR-3 behavior (block + upgrade message) must hold.

## 2. Related Requirements
- User Story: US-REC-010
- Business Rules: BR-3 (block conversion if it would exceed MaxEmployees; show upgrade message)
- Preconditions: story S2 (tenant has not exceeded its max employee limit)

## 3. Preconditions
- Tenant "acme"; applicant {acme_applicantId} Hired with Accepted offer.
- Scenarios set `Tenant.MaxEmployees` and the current active employee count as below.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Scenario A (at limit) | MaxEmployees=50, active count=50 | conversion would make 51 -> blocked |
| Scenario B (one below) | MaxEmployees=50, active count=49 | conversion -> 50 succeeds |
| Scenario C (unlimited) | MaxEmployees=null, active count=10000 | never blocked |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Scenario A: attempt to convert {acme_applicantId} (count 50 == MaxEmployees 50) | Blocked (402/409/422) with a clear "employee limit reached — upgrade your plan" message (BR-3). |

| 3 | Scenario B: convert with count 49, MaxEmployees 50 | Succeeds; active count becomes 50 (the last allowed seat) (BR-3 boundary). |

| 5 | Scenario C: MaxEmployees=null with a large active count | Conversion proceeds; null is treated as UNLIMITED — never blocked. |
| 6 | Verify counting basis | The limit check counts ACTIVE employees consistently (terminated/deactivated employees excluded per the platform's count definition); the check is tenant-scoped (only acme's employees counted). |

## 6. Postconditions
- Conversion blocked exactly at/over MaxEmployees with an upgrade message and no writes; allowed below it; unlimited when null.
