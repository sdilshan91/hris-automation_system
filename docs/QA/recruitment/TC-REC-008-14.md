# TC-REC-008-14: Applicant candidate-portal magic-link is EMAILED on request (DF-41), embeds a genuine `/portal?token=` link, and is suppressed with no dispatch when no application exists (BR-5) — US-REC-008 FR-1

## 1. Test Objective
Verify the DF-41 delivery seam on US-REC-008 FR-1: when an applicant requests a candidate-portal link, the system dispatches **exactly one** `applicant_portal_link` email to the applicant's address, carrying a real, working magic-link URL of the shape `https://{subdomain}.{baseDomain}/portal?token=…` whose token round-trips through `ValidateAsync` (proving the emailed token is the issued token, not a placeholder). The magic-link codec (`PortalMagicLink`) that produces that token must sign/verify a tenant+email+expiry payload, surface the expiry so the service can reject stale tokens, and reject tampered / wrong-secret / malformed tokens. End-to-end through the composed MediatR pipeline, a valid token grants the correct tenant's applicant dashboard, an expired token is rejected (401 `token_expired`), and a Tenant-A token is denied on Tenant-B's subdomain (401 `invalid_token`). Per **BR-5** (anti-enumeration), a request for an email with **no application** issues no token, sends **no email**, yet still returns success so the caller cannot infer whether the email exists. Previously `RequestLinkAsync` was a log-only seam (no email).

## 2. Related Requirements
- User Story: US-REC-008
- Acceptance Criteria: AC-1 (magic link grants the correct applicant's dashboard in the correct tenant)
- Functional Requirement: FR-1 (candidate portal accessible via a unique, time-limited, cryptographically signed magic-link URL sent by email)
- Business Rule: BR-5 (a fresh link is issued only after verifying the email matches an existing application; anti-enumeration)
- Finding: DF-41 (`RequestLinkAsync` now emails the magic link — previously a log-only seam)

## 3. Preconditions
- A tenant "acme" with `Recruitment:PortalTokenSecret` and `Platform:BaseDomain` configured (in-memory config; the HMAC secret is never hardcoded into the service).
- An applicant row exists for the requesting email (for the positive-dispatch arm); no applicant row exists (for the BR-5 arm).
- Delivery is observed through a recording `INotificationDispatcher` (email leg) for the unit arms, and through the real composed pipeline + `ApplicantPortalTokenService`/`ApplicantPortalService` + global query filter for the integration arms.

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Request a portal link for an email that HAS an application. | Exactly one email dispatched, `EventKey == applicant_portal_link`, `RecipientEmail == the applicant`, tenant-stamped; payload embeds `…/portal?token=`; the extracted token validates via `ValidateAsync` and resolves to the applicant email. `RequestLink_WithApplication_DispatchesExactlyOneMagicLinkEmail_ContainingIssuedToken`. |
| 2 | Request a portal link for an email with NO application. | Result is success, `Value == false`, and NO email dispatched (BR-5 anti-enumeration). `RequestLink_WithoutApplication_DoesNotDispatch_ButStillReturnsSuccess_BR5`. |
| 3 | Issue a token then verify it (codec). | Round-trips tenant + lower-cased email + Unix-second expiry. `Issue_ThenVerify_Roundtrips_TenantEmailExpiry`. |
| 4 | Verify a past-expiry token (codec). | Signature verifies (authentic) but surfaces the past expiry for the service to reject. `Verify_ExposesExpiry_SoCallerCanRejectExpiredToken`. |
| 5 | Verify tampered-payload / tampered-signature / wrong-secret / malformed tokens (codec). | All rejected. `Verify_TamperedPayload_IsRejected`, `Verify_TamperedSignature_IsRejected`, `Verify_WithWrongSecret_IsRejected`, `Verify_MalformedToken_IsRejected`. |
| 6 | Hash a token (codec). | Deterministic 64-char SHA-256 hex that does not contain the raw token. `HashToken_IsDeterministic_AndHidesRawToken`. |
| 7 | Present a valid token to the composed portal pipeline. | Returns the correct applicant's sanitized dashboard in the correct tenant. `ValidToken_ReturnsCorrectApplicantDashboard`. |
| 8 | Present an expired token to the pipeline. | 401 `token_expired`. `ExpiredToken_IsRejected`. |
| 9 | Present a Tenant-A token against Tenant-B's subdomain pipeline. | 401 `invalid_token` (cross-tenant denial). `CrossTenantToken_IsDenied`. |
| 10 | Request a link for an existing vs missing email through the pipeline. | Identical generic message either way; a token row is persisted for the existing email only (BR-5). `RequestLink_ReturnsGenericMessage_RegardlessOfExistence`. |
