# TC-REC-006-09: Exactly one scorecard per interviewer per interview -- a second submit edits, not duplicates

## 1. Test Objective
Verify FR-2: each interviewer may have EXACTLY ONE scorecard per interview assignment. A first submission creates the card; a subsequent submission by the same interviewer for the same interview does NOT create a second row -- it is either an edit (within the lock window, per TC-REC-006-08) or rejected (after lock). There can never be two `interview_scorecard` rows for the same (tenant, interview_id, interviewer_employee_id) tuple.

## 2. Related Requirements
- User Story: US-REC-006
- Functional Requirements: FR-2
- Business Rules: BR-4 (edit-vs-immutable interplay)
- Data Requirements: S7 (uniqueness on tenant_id + interview_id + interviewer_employee_id)

## 3. Preconditions
- Tenant "acme" active; empA assigned to interview {acme_interviewId}.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Interview | {acme_interviewId} | empA assigned |
| First submit | 4/4/4/4, Hire | Creates the card |
| Second submit (same interviewer) | 5/5/5/5, Strong Hire | Must NOT create a duplicate |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As empA, `POST` a first scorecard (4/4/4/4, Hire) | 201; one `interview_scorecard` row created. |
| 2 | As empA, `POST` a SECOND scorecard for the same {acme_interviewId} (within lock window) | The system does NOT create a second row -- either 409 "already submitted, use edit" OR it is treated as an update to the existing card (FR-2). EITHER contract is acceptable; what must NOT happen is two rows. |
| 3 | Verify row count | `SELECT count(*) FROM interview_scorecard WHERE tenant_id=acme AND interview_id={acme_interviewId} AND interviewer_employee_id=empA` returns exactly 1 (FR-2). |
| 4 | DB-level uniqueness | A unique constraint/index on (tenant_id, interview_id, interviewer_employee_id) rejects a duplicate insert even if the app guard is bypassed. |
| 5 | Concurrent double-submit | Two near-simultaneous submits from empA result in exactly one persisted card (the second loses to the unique constraint or is folded into an update); no lost data, no duplicate. |

## 6. Postconditions
- Exactly one scorecard exists for (acme, {acme_interviewId}, empA); duplicates are impossible.
