# TC-REC-007-15: A sent offer email embeds the candidate's magic-link (`offer.portalUrl` = `/portal?token=`) so the applicant can respond via the portal; token-issuance failure still sends the offer, without the link — US-REC-007 AC-2 / FR-4/FR-5 (DF-42)

## 1. Test Objective
Verify the DF-42 seam on US-REC-007's offer-send path (AC-2, "Send to Applicant"): when `NotifyOfferAsync("offer-sent", …)` fires, the service mints a candidate portal magic-link token and embeds it into the `offer_sent` email payload as `offer.portalUrl` of the shape `https://{subdomain}.{baseDomain}/portal?token={token}` — the same candidate-portal magic-link mechanism as US-REC-008, delivered here so the applicant can accept/decline the offer from the portal. Critically, the magic-link leg must be **best-effort**: if token issuance FAILS, the offer email is **still sent** (offer delivery must never be broken by the link leg) but carries **no** link (`offer.portalUrl` is blank and the payload contains no `/portal?token=`). This TC binds only the magic-link-embed behaviour; offer-PDF-at-rest / substitution integrity is covered by the sibling TC-REC-007-14, and the offer-send recipient routing / PDF-vs-fallback split by the wider US-REC-007 arms.

> **ID note:** `TC-REC-007-14` was already taken by the existing offer-PDF-at-rest security TC, so this magic-link-embed case takes the next-free suffix `-15`.

## 2. Related Requirements
- User Story: US-REC-007

## 3. Preconditions
- A tenant "acme" with `Platform:BaseDomain` configured; recruitment data (vacancy, applicant, offer) seeded.
- The offer email leg is observed via a recording `INotificationDispatcher` (the no-PDF path falls back to the dispatcher, so the payload — and thus `offer.portalUrl` — is inspectable).
- A fake `IApplicantPortalTokenService` that either issues a fixed token, or fails issuance, to drive both arms.
