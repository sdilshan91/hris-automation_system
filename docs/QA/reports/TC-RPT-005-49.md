# TC-RPT-005-49: Real-Postgres coverage for the dashboard birthday index — migration backfill EXTRACT SQL, the `windowKeys.Contains(BirthMonthDay)` window translation (incl. year-end wrap), and the interceptor round-trip — US-RPT-005 (DF-49)

## 1. Test Objective
Prove on **real Postgres** the index-backed upcoming-birthdays optimization (shipped #390, ISSUE-285a) that InMemory cannot:
- **Migration backfill SQL** — the migration's `UPDATE employees SET birth_month_day = EXTRACT(MONTH FROM date_of_birth)*100 + EXTRACT(DAY FROM date_of_birth)` is the ONLY thing that sets `BirthMonthDay` for pre-existing rows (the interceptor never fires for them). `EXTRACT` is unrunnable on InMemory.
- **Index-backed window query translates** — `windowKeys.Contains(e.BirthMonthDay)` compiles to real SQL on Npgsql and returns only the in-window active/probation employees (a post-query re-filter means deleting the SQL `Where` keeps InMemory green — so the optimization is only *pinned* on real PG).
- **Year-end wrap** — a Dec→Jan window's wrapped key set (`1230,1231,0101…`) also translates and matches.
- **Interceptor round-trip** — a create/update through the real DbContext keeps `birth_month_day` in sync against the real `date` DOB column.

## 4. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Seed a pre-migration-style row (`birth_month_day = 0`, DOB set, interceptor off); run the migration's EXTRACT UPDATE. | `birth_month_day` becomes `month*100+day`. `MigrationBackfill_Extract_SetsBirthMonthDay_ForPreExistingRows`. |
| 2 | Seed in/out-of-window + null-DOB + Terminated employees; run the widget window query. | Only the in-window actives return. `BirthMonthDayWindowQuery_TranslatesToSql_ReturnsOnlyInWindow`. |
| 3 | Dec 30 → Jan 6 window. | Wrapped key set matches. `BirthMonthDayWindowQuery_WrapsYearEnd_OnRealPostgres`. |
| 4 | Create (interceptor) → key stamped; update DOB → key updates; clear DOB → null. | Key stays in sync. `BirthMonthDayInterceptor_KeepsKeyInSync_OnRealPostgres`. |
