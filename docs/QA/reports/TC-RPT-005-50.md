# TC-RPT-005-50: Dashboard widgets load in parallel with per-widget child scopes that RE-SEED the tenant (no cross-tenant leak), plus a startup warmup (DF-50 — US-RPT-005)

## 1. Test Objective
Verify DF-50: the role-based dashboard (`DashboardService.GetWidgetsAsync`) now loads its ~8 widgets in
**parallel** — each widget in its OWN DI scope with a fresh `AppDbContext` + collaborators — via
`IParallelTenantScopeRunner`, bounded by `Dashboard:MaxWidgetParallelism` (default 4). Because a fresh
child scope starts with an **unresolved** `ITenantContext` and the EF global query filter is **fail-open**
(`!IsResolved || TenantId==…` → every tenant's rows), the runner MUST re-seed each child scope's tenant
(`SetTenant`/`SetSystemContext`) from the parent snapshot **before** any query — this is the
leak-prevention gate. A startup `DashboardWarmupHostedService` primes the EF model + query plans + pools
(non-blocking, tenant-agnostic via `IgnoreQueryFilters`) to kill the cold-start outlier; it never blocks
or crashes startup. The prelude (acting employee, has-direct-reports, role) stays sequential; widget set,
order, and null-omit behavior are unchanged.

## 2. Related Requirements
- User Story: US-RPT-005 (role-based KPI dashboard — the default landing page)
- Critical Rule #1: tenant isolation is non-negotiable (BUG-003 class) — enforced per child scope under parallelism
- Finding: DF-50 (dashboard parallelize + cold-start warmup)
- Decision (user, 2026-07-21): warmup + safe parallelize (warm-up fixes the ~25s cold-start; parallelism improves the warm p95)

## 3. Preconditions
- `ParallelTenantScopeRunner` resolvable with the request-scoped `ITenantContext` + `IServiceScopeFactory`.
- Dashboard integration harness on a shared `InMemoryDatabaseRoot` so child-scope contexts see the seeded data (the global query filter applies on InMemory too).
