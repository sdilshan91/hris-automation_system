# TC-NTF-001-07: Mark-read / navigation denied on another user's notification (IDOR)

## 1. Test Objective
Verify a user cannot mark as read (or otherwise act on) a notification that belongs to a
different user, even within the same tenant. Guards against IDOR on the notification id.

## 2. Related Requirements
- User Story: US-NTF-001
- Acceptance Criteria: AC-4, AC-5
- Functional Requirements: FR-7 (mark as read), FR-3 (user-scoped persistence)

## 3. Preconditions
- Tenant A has two users: `emp1` and `emp2`.
- `emp2` owns notification `N-2` (is_read=false). `emp1` is authenticated.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| acting user | emp1 | Tenant A |
| target notification | N-2 | owned by emp2 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As `emp1`, call mark-as-read on notification id `N-2` (direct API/IDOR) | Request denied — 404 (not found in `emp1`'s scope), not 403 that confirms existence |
| 2 | As `emp1`, call "Mark All as Read" | Only `emp1`'s own notifications are affected; `N-2` remains unread |
| 3 | Query `N-2` in DB | is_read still false; unchanged |
| 4 | As `emp1`, attempt to GET / list notification `N-2` directly | Not returned in `emp1`'s list / 404 on direct fetch |
| 5 | As `emp2`, mark `N-2` read | Succeeds — owner can act on own notification (sanity) |

## 6. Postconditions
- `emp2`'s notification untouched by `emp1`; only the owner can mutate it.
