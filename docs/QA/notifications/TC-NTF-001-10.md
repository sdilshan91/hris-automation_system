# TC-NTF-001-10: SignalR reconnection with exponential backoff; missed notifications delivered

## 1. Test Objective
Verify the SignalR client gracefully handles disconnection and automatically reconnects using
exponential backoff, then receives any notifications missed during the outage on reconnect.
Implements the "Reconnection" test hint. Also exercises NFR-5 polling fallback.

## 2. Related Requirements
- User Story: US-NTF-001
- Acceptance Criteria: AC-1, AC-2
- Functional Requirements: FR-9 (auto-reconnect, exponential backoff), FR-10 (Redis backplane)
- Non-Functional: NFR-5 (degrade to 30s polling if WebSocket unavailable)

## 3. Preconditions
- `emp1` (Tenant A) connected to `/hubs/notifications`; badge = 0.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| outage trigger | drop WS / restart hub / brief Redis kill | simulate disconnect |
| notifications during outage | 2 | sent while disconnected |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Force a SignalR disconnect (drop the WebSocket) | Client enters Reconnecting state; UI does not crash |
| 2 | Observe reconnection attempts | Retries follow exponential backoff (increasing intervals, not a tight loop) |
| 3 | While disconnected, generate 2 notifications for `emp1` | Notifications are persisted server-side |
| 4 | Restore the hub/backplane | Client reconnects and re-joins `t:TA:user:emp1` and role group |
| 5 | Observe `emp1`'s client after reconnect | Badge reflects the 2 missed notifications (fetched on reconnect); items visible in the panel |
| 6 | Simulate WebSocket entirely unavailable (transport blocked) | Client degrades to polling every ~30s and still surfaces new notifications (NFR-5) |

## 6. Postconditions
- Client reconnected; no notifications lost; backoff observed.
