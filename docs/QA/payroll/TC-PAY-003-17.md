# TC-PAY-003-17: Per-runId interlock prevents concurrent payroll reprocess from duplicating slips (DF-61-conc)

## 1. Test Objective
Verify on **real Postgres** that `PayrollRunProcessor.ProcessAsync` holds a per-runId session advisory lock so two concurrent executions on the SAME run cannot both replace-clean and re-insert slips (which would produce duplicate `ReviewPending` slips — never a double-pay, but wrong), while runs with DIFFERENT ids are never serialized against each other, and the retry-after-completion edge (a run whose reprocess is already satisfied) no-ops instead of re-duplicating.

## 2. Related Requirements
- User Story: US-PAY-003
- Acceptance Criteria: AC-3 (run processing), payroll reprocess correctness
- Deferred follow-up: DF-61-conc (decision: per-runId mutex; user-ruled 2026-07-22)
- Standard: IEEE 829

## 3. Preconditions
- Docker available; Testcontainers `postgres:17-alpine` (session advisory locks require real Postgres).
- A raw `NpgsqlConnection` able to hold the same advisory key to simulate a concurrent worker.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Lock key | `payroll_run_process:{runId}` | `hashtext(...)` → advisory lock |
| Skip sentinel | CompletedAt / TotalGross | overwritten only if re-processed |
| Run statuses | Queued / ReviewPending | proceed vs skip |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Hold the run's advisory lock from a separate Npgsql session; call `ProcessAsync` on the same run. | Returns success but NO-OPs: the run stays `Queued` with 0 slips (the loser did nothing — did not merely "not throw"). |
| 2 | Release the lock; call `ProcessAsync` again. | The run processes to `ReviewPending` (the interlock is not a permanent block). |
| 3 | Hold run A's lock; call `ProcessAsync` on a DIFFERENT run B. | Run B reaches `ReviewPending` while A stays `Queued` — different runIds are not serialized. |
| 4 | Call `ProcessAsync` on a ReviewPending run whose `ReprocessRequestedAt` is NULL (already satisfied), with sentinel CompletedAt/TotalGross. | The run is skipped: CompletedAt/TotalGross are unchanged (a re-run would have reset them) — no re-duplication. |
| 5 | Call `ProcessAsync` on a ReviewPending run WITH a marker set (a due rerun). | Proceeds, recomputes, and clears the marker to null. |

## 6. Postconditions
- Concurrent reprocess of the same run cannot duplicate slips; distinct runs are unaffected; the already-satisfied edge is safe.
- Known LOW residuals: DF-61-conc-retry (retry-reconnect can move work off the lock-holding connection; sweep backstops) and DF-61-conc-slip (a real-slip duplication arm) — see the register.
