# TC-PAY-008-14: The payroll "pending approvals" queue returns only the runs the current approver can actually approve — mirroring the ApproveAsync eligibility gates (step-role, maker-checker + small-team, distinct-approver), tenant-scoped — US-PAY-008 AC-4 / BR-5 (DF-14)

## 1. Test Objective
Verify the DF-14 approver-scoped read-endpoint `GET /api/v1/payroll/approval/pending`. Previously the FE Pending-Approvals queue called `GET /payroll/runs?status=AwaitingApproval`, but the backend ignored the param and returned **every** run for the tenant — so every approver saw runs they could not approve. The new `PayrollApprovalService.GetPendingApprovalsAsync` returns a run **iff calling approve on it would not 403**, mirroring the three `ApproveAsync` gates exactly (one shared source of truth):

- **Step-role (AC-4/FR-2).** If the run's current approval step has a configured role (`PayrollApprovalStepConfig.RoleId`), the run appears only when the caller holds that role (`UserHoldsRoleAsync`); a step with no config row imposes no per-step restriction.
- **Maker-checker (BR-5).** The caller's **own** submission is excluded when the tenant has **≥2** eligible approvers (`CountEligibleApproversAsync`); the **small-team exception** (<2 eligible) lets the submitter see/approve their own run.
- **Distinct-approver (AC-4).** For multi-step runs, a run the caller has **already approved** at an earlier step is excluded (shared `HasCallerAlreadyApprovedAsync` predicate — the same one `ApproveAsync` enforces).

Only `AwaitingApproval` runs surface; the submitter display name is resolved via a batched (no-N+1) Employee-then-User lookup; the queue is tenant-scoped by the global query filter.
