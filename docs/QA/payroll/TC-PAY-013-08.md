# TC-PAY-013-08: F&F policy configuration VALIDATION — effective date is required, a same-effective-date re-config replaces the prior version, and the effective policy resolves latest-≤-asOf (or the safe default)

## 1. Test Objective
Verify the policy-configuration **validation + integrity** behind AC-1/AC-2 (the config surface the settlement reads), which the computation TCs (TC-PAY-013-01/02) do not exercise:
1. **Structural validation** — a policy version submitted with **no effective date** is rejected (`CreateFnFPolicyValidator`, the only hard rule; the include toggles are always-valid booleans).
2. **One version per effective-from date (money-adjacent)** — configuring a policy on an effective date that already has a version **replaces** (soft-deletes) the prior one, so two same-date active versions never coexist. Without this, the resolver's `OrderByDescending(EffectiveFrom).First()` would tie-break **non-deterministically** between two same-date rows on a money path.
3. **Effective resolution** — `GetEffectiveAsync(asOf)` returns the latest version with `EffectiveFrom ≤ asOf`, and returns the **safe code-default** (all components on) when no policy is configured (the feature works without seeding).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Invalid version | effective_from = `default(DateOnly)` | must be rejected (structural rule) |
| Same-date v1 | effective_from 2026-06-01, encashment = ON | first configured version |
| Same-date v2 | effective_from 2026-06-01, encashment = OFF | re-config on the same date → replaces v1 |
| Resolution seed | v(2026-01-01, encash ON) + v(2026-06-01, encash OFF) | two distinct dates |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Submit a `CreateFnFPolicyCommand` with `effective_from = default` (no date). | Validation FAILS ("Effective-from date is required."); the version is not created (AC-1). |
| 2 | Submit a `CreateFnFPolicyCommand` with a real effective date. | Validation PASSES (AC-1). |
| 3 | Configure a policy on 2026-06-01 (encashment ON), then configure another on the **same** 2026-06-01 (encashment OFF). | Exactly **one** active (non-deleted) `TenantFnFPolicy` row exists for 2026-06-01 — the prior was soft-deleted, not accumulated (AC-1/AC-2, one-version-per-date). |
| 4 | Resolve the effective policy on/after 2026-06-01. | The **replacement** (encashment OFF) governs — deterministically, with no tie-break ambiguity (AC-2). |
| 5 | With **no** policy configured, resolve the effective policy for any date. | The safe code-default governs: pro-rated + statutory + encashment all ON (AC-2 — works without seeding). |
| 6 | Configure v(2026-01-01, encash ON) + v(2026-06-01, encash OFF); resolve as-of 2026-03-01, then as-of 2026-08-01. | As-of 2026-03-01 → the **January** version (encashment ON); as-of 2026-08-01 → the **June** version (encashment OFF) — latest `EffectiveFrom ≤ asOf` wins (AC-2). |

## 6. Postconditions
- Invalid policy config is rejected; a same-date re-config leaves exactly one active version; the effective resolution is deterministic (or the safe default) — the config surface the settlement reads is sound.
