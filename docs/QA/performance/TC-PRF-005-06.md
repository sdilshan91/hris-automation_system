# TC-PRF-005-06: With anonymity ON, the results API does NOT expose reviewer_id — enforced server-side, not just UI (FR-5/NFR-3/BR-5)

## 1. Test Objective
Verify FR-5 / NFR-3 / AC-3 / AC-4: when tenant/cycle anonymity is enabled, reviewer identity is not revealed to the employee or manager in the results view, and this is enforced at the API/database level (the response payload must not contain `reviewer_id` or any identifying field) — not merely hidden in the UI. This is the single most important anonymity test: a UI-only hide would still leak identity to anyone inspecting network traffic.

## 2. Related Requirements
- User Story: US-PRF-005
- Acceptance Criteria: AC-3, AC-4
- Functional Requirements: FR-5
- Non-Functional Requirements: NFR-3
- Business Rules: BR-5
- Data Requirements: S7 (feedback_360 anonymity flag)

## 3. Preconditions
- 360-enabled cycle "FY26 Annual Review" active for acme with anonymity ENABLED.
- Liam Carter under review; peers Ava + Ben and reports Sara + Tom have submitted.
- HR Officer "Nadia Khan" (`Performance.Review.All`), the manager "Maya Shah", and the employee "Liam Carter" each authenticated in acme.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Anonymity | ON | tenant/cycle setting |
| Viewers | Liam (self), Maya (manager), Nadia (HR) | results consumers |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As the employee Liam, `GET .../performance/360/{liamId}/results` and inspect the raw JSON | Per-reviewer comments/ratings are present but NO `reviewer_id`, reviewer name, email, avatar, or any identifying field is in the payload; comments are grouped by category only (Peer/Report), not by person (FR-5, NFR-3). |
| 2 | Repeat as the manager Maya | Same — manager view is also stripped of reviewer identifiers under anonymity. |
| 3 | Inspect with browser devtools / a raw HTTP client (not the SPA) | The server-side projection omits reviewer identifiers; identity is NOT merely CSS-hidden in the DOM — the payload itself never carries it (NFR-3: not exposed even in debug mode). |
| 4 | Confirm the underlying row still stores reviewer_id | At the DB level `feedback_360.reviewer_id` is populated (needed for BR-3 dedupe + reminders), but the anonymized results projection never returns it to employee/manager. |
| 5 | As HR with an explicit non-anonymized admin view (if the implementation provides one) | Reviewer identity may be visible ONLY through a documented, separately-permissioned admin path; the standard employee/manager results endpoint never returns it. (If no such admin path exists, this step is N/A.) |

## 6. Postconditions
- Reviewer identity is never exposed via the standard results API under anonymity; the anonymity flag is honored at the projection layer.
