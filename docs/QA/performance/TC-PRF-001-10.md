# TC-PRF-001-10: Optimistic concurrency — two sessions editing the same employee's goals (NFR-4)

## 1. Test Objective
Verify NFR-4: goal operations are protected with optimistic concurrency control to prevent lost updates. When two sessions load the same employee's goals and both save, the second (stale) save is rejected with a concurrency conflict rather than silently overwriting the first.

## 2. Related Requirements
- User Story: US-PRF-001
- Non-Functional Requirements: NFR-4
- Functional Requirements: FR-1

## 3. Preconditions
- Manager "Ravi Kumar" authenticated in acme in two browser sessions (S1, S2) with `Performance.SetGoal.Team`; window OPEN; Asha has an existing goal set (with a version/row-version token).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Goal under edit | Asha's "Revenue target" | both sessions load the same goal/version |
| S1 edit | weight 40 -> 45 (and rebalance) | saved first |
| S2 edit | weight 40 -> 35 (and rebalance) | stale version on save |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | S1 and S2 both load Asha's goals; note both responses carry the same concurrency token (rowversion/`updated_at`/ETag). | Both sessions hold version V1. |
| 2 | In S1, edit the goal set and Save (rebalanced to 100%) | 200; goals updated; server bumps the version to V2. |
| 3 | In S2 (still holding V1), edit and Save | 409 Conflict (optimistic concurrency) — the stale V1 token is rejected (NFR-4); S1's changes are NOT lost. |
| 4 | S2 reloads, sees V2 (S1's changes), reapplies its edit, Saves | 200 — succeeds against the current version; no lost update occurred. |
| 5 | Verify persistence | Final goal state reflects both edits applied in order; no silent overwrite of S1's save. |

## 6. Postconditions
- Concurrent edits are serialized via optimistic concurrency; lost updates are prevented.
