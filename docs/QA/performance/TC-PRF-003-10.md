# TC-PRF-003-10: Optimistic concurrency -- HR and the manager edit the same review simultaneously; the stale save is rejected (409), no lost update

## 1. Test Objective
Verify NFR-3: the system uses optimistic concurrency control (rowversion/ETag) so that when HR and the manager edit the same review record at the same time, the second (stale) write is rejected with a conflict (409) rather than silently overwriting the first. No update is lost; the conflicting user is told to reload and re-apply.

## 2. Related Requirements
- User Story: US-PRF-003
- Non-Functional Requirements: NFR-3
- Functional Requirements: FR-1

## 3. Preconditions
- acme cycle FY26-H1; an in-progress (reopened/draft) manager review for Asha exists.
- HR Officer Nadia (`Performance.Review.All`) and Manager Ravi (`Performance.Review.Team`) both have edit access to it.
- The review carries a concurrency token (rowversion/ETag).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Session A | Ravi | loads review at version V1 |
| Session B | Nadia | loads same review at version V1 |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Ravi and Nadia both open Asha's review (both read version V1) | Both load the same data + concurrency token V1. |
| 2 | Ravi changes Goal 1's rating and saves | Save succeeds; the review's version advances to V2; Ravi's change persists. |
| 3 | Nadia (still on V1) changes Goal 2's comment and saves | Save is rejected with 409 Conflict (stale token); Nadia's write does NOT overwrite Ravi's; the message prompts a reload. |
| 4 | Nadia reloads (gets V2 with Ravi's change), re-applies her Goal 2 edit, and saves | Save now succeeds at V2 -> V3; both Ravi's and Nadia's changes are present (no lost update). |

## 6. Postconditions
- Concurrent edits are serialized via the concurrency token; the stale write is rejected; both intended changes survive after reload-and-retry.
