# TC-ADM-004-02: Suspend a past_due tenant (alternative valid transition past_due -> suspended)

## 1. Test Objective
Verify BR-1's alternative valid suspension entry point: a tenant in `past_due` status can be suspended (e.g. for unresolved payment failure). The same suspension effects as TC-ADM-004-01 apply (status change, fields, token revocation, lifecycle event, audit).

## 2. Related Requirements
- User Story: US-ADM-004
- Acceptance Criteria: AC-1
- Functional Requirements: FR-1, FR-7
- Business Rules: BR-1 (past_due -> suspended), BR-5

## 3. Preconditions
- System Admin authenticated with `SystemAdmin`.
- Tenant "Beta" exists, `status = PastDue`, non-system, with active user sessions.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| tenant_id | beta-tenant-uuid | past_due, non-system |
| reason | "Payment failed 3 cycles — auto-suspend per policy" | >= 10 chars |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | `POST /api/v1/admin/tenants/{id}/suspend` with `{ reason }` against the past_due tenant | 200/204; transition accepted (past_due is an allowed source per BR-1). |
| 2 | Re-read the tenant | `status = Suspended`; `SuspendedAt`/`SuspendedReason` set. |
| 3 | Query refresh tokens + lifecycle event + audit | Tokens revoked; `event_type = 'suspended'` row written; `system_audit_log` entry present. |

## 6. Postconditions
- Beta is `Suspended` via the past_due path; identical downstream effects to the active-source case.
