# TC-ADM-009-14: [DEFERRED] Runtime module gating — disabled module's API endpoints + Angular routes blocked per tenant

## 1. Test Objective
Verify BR-6 + the FR-6 runtime aspect + the "Module gating" Test Hint: for a tenant provisioned on a plan WITHOUT a given module (e.g. Recruitment), that module's API endpoints AND Angular lazy-loaded routes are inaccessible for that tenant.

DEFERRED — status: blocked. The plan's `enabled_modules` ARE stored and `Tenant.EnabledModules` IS derived at provisioning (asserted run-green in TC-ADM-009-06/-11). What is deferred is the cross-cutting RUNTIME ENFORCEMENT: an ASP.NET Core authorization policy / middleware that gates EVERY module's controllers by the tenant's entitlement, plus the Angular route guard that blocks the disabled module's lazy route. That enforcement spans all feature modules and is a large cross-cutting concern not built in this story.

## 2. Related Requirements
- User Story: US-ADM-009
- Business Rules: BR-6 (enabled_modules gate Angular modules + API endpoints per tenant)
- Functional Requirements: FR-6 (enabled_modules — runtime gating portion)
- Test Hints (Module gating)
- Dependencies: §9 (module gating middleware in Angular + ASP.NET Core)

## 3. Preconditions
- (Deferred prerequisite) A module-entitlement authorization policy on every controller + an Angular route guard reading the tenant's EnabledModules.
