# TC-ADM-002-01: Monitoring dashboard loads with correct platform health roll-up and aggregate counts (happy path)

## 1. Test Objective
Verify the primary success flow of AC-1 for the metrics the platform builds FOR REAL: an authenticated System Admin opens the Monitoring dashboard and sees the overall platform-health roll-up (healthy / degraded / down), active tenant count, total active user count, tenant-status breakdown, DB health, Redis health, and Hangfire job-queue counts. All numbers reconcile with the seeded platform state. (The error-rate %, P95 latency, SLA and trend widgets are covered as Deferred in TC-ADM-002-14..18.)

## 2. Related Requirements
- User Story: US-ADM-002
- Acceptance Criteria: AC-1
- Functional Requirements: FR-1 (real subset: health roll-up + DB/Redis/Hangfire), FR-5, FR-6
- Business Rules: BR-1
- Data Sources: PostgreSQL (`tenant`), health checks (`/health/ready`), Hangfire storage

## 3. Preconditions
- System Admin "Olivia Park" is authenticated at `admin.yourhrm.com` with a valid system-tenant JWT carrying the `SystemAdmin` role claim.
- A known platform state is seeded: e.g. 6 tenants — 4 active, 1 trial, 1 suspended — with a total of 12 active users across them.
- The DB is reachable; Redis is either configured-and-reachable or not configured (record which).
- Hangfire storage is reachable with a known job mix (e.g. 2 queued, 1 processing, 40 succeeded, 1 failed).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Tenants | 6 total: 4 active, 1 trial, 1 suspended | drives count + status breakdown |
| Active users | 12 | cross-tenant aggregate |
| DB | reachable | health = healthy |
| Redis | configured & reachable (or "not configured") | health = healthy or "not configured" |
| Hangfire | queued 2 / processing 1 / succeeded 40 / failed 1 | drives job-status card |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Navigate to `https://admin.yourhrm.com/monitoring`; observe `GET /api/v1/admin/monitoring/overview` | Request carries the system-tenant bearer; response 200 with a platform-health object, counts, status breakdown, DB/Redis health, Hangfire counts. |
| 2 | Read the platform-health roll-up KPI | Shows an overall status of `healthy` (all dependency checks pass). If any dependency is degraded/down the roll-up reflects the worst dependency. |
| 3 | Read the active-tenant and active-user KPIs | Active tenants = 5 (4 active + 1 trial, excluding the suspended one per the platform's "active" definition); total active users = 12. Counts reconcile with the DB. |
| 4 | Read the tenant-status breakdown | Breakdown shows active 4, trial 1, suspended 1 (sums to the 6 total tenants). |
| 5 | Read the DB health indicator | DB shows `healthy` (green), sourced from `/health/ready`. |
| 6 | Read the Redis health indicator | Redis shows `healthy` if configured & reachable, OR an explicit `not configured` state — never a fabricated green when no Redis is wired. |
| 7 | Read the Hangfire job-status card | Shows queued 2, processing 1, succeeded 40, failed 1, matching Hangfire storage (FR-5). |
| 8 | Note the "last updated" timestamp on the dashboard | A recent timestamp is shown, establishing the baseline for the polling-refresh test (TC-ADM-002-07). |

## 6. Postconditions
- Dashboard reflects true seeded platform state; no fabricated metrics. A `Monitoring.Viewed` audit record is written (asserted in TC-ADM-002-11).
