# TC-ADM-008-22: The runtime DB role can APPEND to the audit tables but cannot rewrite or erase them, while the privileged role can still purge (BUG-301 / GAP-005)

## 1. Test Objective
Verify the database-layer half of AC-5 / NFR-3 as it is now specified: on a real PostgreSQL where the
production role split is in force, the **runtime** role `hrm_app` holds `SELECT` + `INSERT` on `audit_logs`
and `employee_field_audit_logs` but **not** `UPDATE` or `DELETE`, a real `UPDATE` from that role is refused
with SQLSTATE `42501`, and the **privileged** role `hrm_owner` retains `DELETE` so the retention purge
(FR-6, `AuditLogPurgeService`) keeps working.

This closes **BUG-301 / GAP-005**: audit immutability used to rest solely on the absence of an update/delete
endpoint (`AuditLogController.cs:19-21` — *"append-only by code convention … REVOKE DEFERRED"*) while
`roles.sql` granted `SELECT, INSERT, UPDATE, DELETE` on **all** tables to `hrm_app`. Anything holding the
app's credentials — a SQL-injection foothold, a stray `ExecuteDelete`, a leaked connection string — could
silently rewrite the one record class the rest of the compliance story depends on. The fix is the REVOKE
block at `HRM.Infrastructure/Persistence/Rls/roles.sql:70-71`, placed **after** the deliberately broad grant
it must override.

> **Scope limitation — read this before citing the TC (see §8).** The automated arm proves the *intended
> privilege set* and PostgreSQL's enforcement of it. It does **not** prove that `roles.sql` produced that
> privilege set in any environment: the test fixture **hand-mirrors** the REVOKE, and `roles.sql` itself is
> executed by nothing in the repo.

## 3. Preconditions
- A real PostgreSQL 17 container (Testcontainers). Privilege bits are a database-engine concept; the EF
  InMemory provider models none of them, so this arm runs on the orchestrator's Postgres run, not on the
  Docker-less agent verify gate.
- The fixture provisions the two production login roles as the superuser — `hrm_app` (LOGIN, `NOBYPASSRLS`,
  the runtime path) and `hrm_owner` (LOGIN, `BYPASSRLS`, migrations/seed/system/jobs) — then applies the
  broad grant, then the audit REVOKE, in the same order as `roles.sql`
  (`RlsIsolationPostgresTests.cs:96-137`).
- Migrations applied; at least one `audit_logs` row exists for the `UPDATE` attempt to be a real statement
  rather than a no-op parse.

## 5. Test Steps
| Step | Action | Expected Result | Automated by |
|------|--------|-----------------|--------------|
| 1 | For each audit table, probe `has_table_privilege('hrm_app', table, 'SELECT')` and `'INSERT'`. | Both **true** — the app writes an audit row on essentially every request, so an over-broad revoke would take the product down rather than harden it. | `RlsIsolationPostgresTests.AuditTables_AreAppendOnly_ForTheRuntimeRole_ButPurgeableByOwner_GAP005` |
| 2 | For each audit table, probe `has_table_privilege('hrm_app', table, 'UPDATE')` and `'DELETE'`. | Both **false** — the runtime role can neither rewrite nor erase audit history (AC-5 / NFR-3). | same arm |

## 6. Postconditions
- In an environment where the two-role split is provisioned, the application's own credentials cannot alter
  or delete audit rows; only the privileged role can, and the only code that does (`AuditLogPurgeService`,
  reached by `AuditLogPurgeJob` after `SetSystemContext()`) already runs there.

## 8. Automation, Traceability, and what this TC does NOT prove
- **Automated-by (green on the orchestrator's real-Postgres run):**
  `src/backend/HRM.Tests/Integration/RlsIsolationPostgresTests.cs:431` →
  `AuditTables_AreAppendOnly_ForTheRuntimeRole_ButPurgeableByOwner_GAP005`.
- **Trait binding:** the arm inherits the **class-level** `[Trait("TC", "TC-PLT-002-RLS")]`
  (`RlsIsolationPostgresTests.cs:46`); it carries no arm-level trait, so a runner cannot select
  `TC-ADM-008-22` by id. An arm-level `[Trait("TC", "TC-ADM-008-22")]` — the precedent already used in this
  file for `TC-ATT-162` at `:564` — would restore id-based selection. That is a `src/` change and is
  flagged to the caller rather than made here.
- **⚠ LIMITATION 1 — the fixture hand-mirrors `roles.sql`; it does not execute it.** The REVOKE asserted
  above is re-declared in the test setup (`RlsIsolationPostgresTests.cs:132-137`) because `roles.sql` uses
  psql-only constructs (`\gexec`, `:'var'` variable interpolation) that Npgsql cannot run; the mirror hazard
  is flagged in a comment at `:120-124`. **Consequence:** this arm proves that *the intended privilege set
  behaves correctly under PostgreSQL*, not that `roles.sql` is what establishes it. A future edit to
  `roles.sql` that dropped or mis-ordered the REVOKE would leave this arm **green**. The two must be
  changed together.
- **⚠ LIMITATION 2 — `roles.sql` is executed by nothing in the repository.** It is not run by the
  application, by EF migrations, by `ops/`, by `scripts/`, or by CI; it is a **manual DBA bootstrap**, run
  once per database, documented in [`docs/DEV/PRODUCTION-CHECKLIST.md`](../../DEV/PRODUCTION-CHECKLIST.md)
  (§ "run once per database by a DBA", plus verification step d2). **Consequence:** in any environment where
  that script has not been run — or where the application connects as a superuser or as the schema owner
  rather than as `hrm_app` — the revoke is simply absent and audit immutability reverts to the code
  convention of [TC-ADM-008-17](TC-ADM-008-17.md). Whether the control is live in a given environment is an
  **ops verification**, not something any automated arm in this repository currently establishes.
- **Manual/ops evidence recorded on the finding (not a test execution record, and not re-run for this TC):**
  BUG-301's close-out reports a one-off check on the live RLS-on dev database on 2026-08-08 — `hrm_app`
  received `42501` on both `UPDATE` and `DELETE` while retaining `SELECT`, `hrm_owner` deleted normally, and
  a real login through the running API still wrote its audit row. Cited here for provenance only; it is a
  point-in-time manual check, not a repeatable gate.
- **[TC-ADM-008-18](TC-ADM-008-18.md) stays `blocked` and is NOT superseded.** Two things it asks for are
  still unproven: (a) enforcement in a **deployed** environment, which Limitation 2 puts outside automated
  coverage, and (b) the **security-event log** of a denied tamper attempt — the database raises `42501`, but
  nothing in the application observes that denial and records it as a security event.
