# TC-ADM-009-19: Plan-limit resolution keeps "plan_id matches no plan" distinct from "plan found with a NULL (unlimited) limit" — an unresolvable plan is a configuration error, not an unlimited allowance (BUG-307)

## 1. Test Objective
Verify that the shared plan-limit resolver reports the **reason** a limit came back empty, so a broken
`tenant.plan_id` can never masquerade as a deliberate "unlimited".

Before the fix, ten call sites each hand-wrote
`SubscriptionPlans.Where(p => p.Code == tenant.PlanId).Select(p => (long?)p.SomeLimit).FirstOrDefaultAsync(ct)`.
`FirstOrDefaultAsync` returns `null` for **two different situations** — *no plan row* and *plan row whose
limit column is NULL* — and every call site read both as "unlimited". They are not the same thing: the
`enterprise` plan genuinely ships `max_employees = NULL` (BR-3, NULL means unlimited), which is exactly why
no call site could tell a deliberate unlimited from a mis-set `plan_id`. Measured on the running database
before the fix: 2 of 3 tenants carried `plan_id = 'default'`, matching no `subscription_plans` row, so every
paid cap silently resolved to unlimited — a revenue rule failing **open**, with no error and no log.

This test case documents the three layers of the shipped fix and the automated arms that pin each of them:
1. **Seeder** — new tenants are seeded onto a plan code that actually exists (`enterprise`), instead of the
   unresolvable `default` (`DbInitializer.cs:49,461,474,1065`).
2. **Startup reconciler** — `DbInitializer.EnsureResolvablePlanIdAsync` (`DbInitializer.cs:735-757`, invoked
   per tenant at `:711`) repoints an already-broken `plan_id`, **preserving the tenant's existing uncapped
   behaviour** and logging a WARNING (silently capping a live tenant at startup would be the opposite and
   worse mistake).
3. **Shared resolver** — `PlanLimitLookup.ResolveAsync` returns `EffectivePlanLimit` exposing
   `IsConfigurationError` vs `IsUnlimited` (`PlanLimitLookup.cs:48-64`); all ten previously-duplicated call
   sites now use it, and a build-breaking guard blocks an eleventh copy of the ambiguous projection.

## 2. Related Requirements
- User Story: US-ADM-009 (System Admin Manages Subscription Plans)
- Acceptance Criteria: **AC-3** (limits are read from the plan **at runtime**, so plan data must resolve),
  **AC-5** (`plan_limit_override` is consulted before the plan at runtime)
- Functional Requirement: **FR-4** (runtime resolution order: non-expired `plan_limit_override` > `subscription_plan` field)
- Business Rule: **BR-3** (`NULL` limit values mean "unlimited")
- Related story: US-ADM-012 AC-3 (usage limits enforced at runtime — this is the resolution layer those
  enforcement points depend on)
- Finding: **BUG-307** (a tenant's `plan_id` could reference no `subscription_plans` row, and "plan not
  found" was indistinguishable from "plan found with a NULL limit")

## 3. Preconditions
- A real PostgreSQL instance (Testcontainers `postgres:17-alpine`) with `subscription_plans`, `tenants` and
  `plan_limit_overrides` created; `TenantInterceptor` + `AuditInterceptor` registered as in production.
- Seeded fixture: plan `starter` (`max_employees = 25`), plan `enterprise` (`max_employees = NULL`, a
  **deliberate** unlimited); tenants `capped` → `starter`, `unltd` → `enterprise`, `broken` → `default`
  (matches no plan).
- The usage-guard arms need no database — they scan the `HRM.Api` / `HRM.Application` / `HRM.Domain` /
  `HRM.Infrastructure` sources (EF migrations excluded) and run in the default Docker-free suite.

## 6. Postconditions
- No tenant can hold a `plan_id` that matches no plan: the seeder never creates one, and the startup
  reconciler repoints (loudly, at WARNING) any that pre-exist, without changing the tenant's effective cap.
- Every plan-limit call site resolves through one shared lookup that reports *why* a limit is empty, so
  "misconfigured" fails closed at the caller while "deliberately unlimited" (BR-3) and "explicit override"
  (FR-4) continue to permit.
- The old ambiguous idiom cannot re-enter production code without failing the build.
