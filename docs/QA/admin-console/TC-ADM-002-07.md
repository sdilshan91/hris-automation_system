# TC-ADM-002-07: Dashboard auto-refreshes via polling and updates the "last updated" timestamp

## 1. Test Objective
Verify the refresh mechanism of AC-1 as implemented FOR REAL: the dashboard re-fetches metrics on a polling interval (NOT SignalR), and on each successful poll the "last updated" timestamp advances and changed counts are reflected. SignalR push (NFR-2) is NOT implemented; this test asserts polling behavior.

## 2. Related Requirements
- User Story: US-ADM-002
- Acceptance Criteria: AC-1
- Functional Requirements: FR-1 (refresh subset)
- Note: NFR-2 SignalR push is deferred; refresh is via polling.

## 3. Preconditions
- System Admin authenticated; Monitoring dashboard open with a known polling interval (default 30s, or a shortened interval for test).
- A baseline "last updated" timestamp and baseline counts are visible.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| Polling interval | 30s default (configurable) | test may shorten |
| Mutation | add 1 active employee to tenant "acme" | changes a gauge between polls |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Record the current "last updated" timestamp and Acme's employee gauge | Baseline captured. |
| 2 | Observe network traffic over one interval | A repeat `GET /api/v1/admin/monitoring/overview` fires automatically after the interval — confirming polling, with NO active WebSocket/SignalR connection present. |
| 3 | After a poll completes, re-read the "last updated" timestamp | The timestamp advances to the latest successful poll time. |
| 4 | Between polls, add 1 active employee to Acme; wait for the next poll | After the next poll, Acme's employee gauge reflects the new count (e.g. 4 -> 5) without a manual page reload. |
| 5 | (Optional) Trigger a manual "Refresh" control if present | An immediate fetch occurs and the timestamp updates. |

## 6. Postconditions
- Dashboard stays current via polling; timestamp and gauges update without full reload.
