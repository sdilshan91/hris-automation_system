# TC-ADM-009-05: Code immutability — update cannot change `code` after creation

## 1. Test Objective
Verify FR-3 + BR-5: the `code` field is immutable after creation (to prevent breaking tenant references). An update that attempts to change `code` is either rejected or silently ignores the code field, while other editable fields update normally.

## 2. Related Requirements
- User Story: US-ADM-009
- Functional Requirements: FR-3 (code immutable after creation)
- Business Rules: BR-5 (code cannot be reused/changed)

## 3. Preconditions
- System Admin "Pat" authenticated at `admin.yourhrm.com` with `SystemAdmin`.
- Plan `growth` exists (code=`growth`).

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| original code | growth | immutable |
| update payload code | growth-renamed | attempted change |
| update payload name | "Growth (Renamed)" | editable |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | As Pat, PUT update `growth` with code=`growth-renamed` and name=`Growth (Renamed)` | Either 400 (code is immutable, request rejected) OR 200 with the code field ignored. |
| 2 | GET the plan | code remains `growth` (unchanged). |
| 3 | Inspect editable fields | If the update was accepted (200 path), name updated to "Growth (Renamed)"; otherwise name unchanged with the request rejected. The behavior is consistent and documented. |
| 4 | Confirm tenants referencing `growth` | Still resolve their plan by code `growth` — no broken references. |

## 6. Postconditions
- Plan code is unchanged; references intact.
