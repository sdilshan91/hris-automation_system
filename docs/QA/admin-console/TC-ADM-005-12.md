# TC-ADM-005-12: Deactivation isolation — disabling a user in Tenant A leaves their Tenant B membership/login intact

## 1. Test Objective
Verify AC-4 / Test-Hint "Deactivation isolation": when a user with memberships in two tenants is deactivated in Tenant A, their Tenant B membership stays `active`, their Tenant B sessions remain valid, and they can still log into Tenant B. Token revocation on deactivation is scoped to the acting tenant only.

## 2. Related Requirements
- User Story: US-ADM-005
- Acceptance Criteria: AC-4
- Business Rules: BR-1
- Test Hints: Deactivation isolation

## 3. Preconditions
- User "Sam" has active memberships in BOTH Acme (Tenant A) and Beta (Tenant B), with live sessions in each.
- Tenant Admin "Dana" authenticated on Acme; a separate Tenant Admin governs Beta.

## 4. Test Data
| Field | Value | Notes |
|-------|-------|-------|
| user | sam | dual-tenant member |
| deactivate in | Acme (A) | |
| must stay intact | Beta (B) | |

## 5. Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Confirm Sam's Beta membership `active` and a live Beta refresh token exist | Baseline recorded. |
| 2 | As Dana, deactivate Sam in Acme | 200; Acme membership `disabled`; Acme tokens revoked. |
| 3 | Query Sam's Beta `user_tenant` | Still `active` — unchanged. |
| 4 | Query Sam's Beta refresh tokens | Still valid — NOT revoked (revocation was Acme-scoped). |
| 5 | As Sam, log in to `beta.yourhrm.com` | Succeeds — Beta access unaffected. |
| 6 | As Sam, attempt Acme login | Rejected — Acme disabled. |

## 6. Postconditions
- Sam: disabled in Acme, fully functional in Beta. No cross-tenant bleed of deactivation.
