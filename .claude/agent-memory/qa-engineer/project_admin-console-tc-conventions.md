3-matrix update rule (same as other modules): per-TC files in `test-cases/admin-console/` + module `TEST-MATRIX.md` + a new module section in the root `test-cases/TRACEABILITY-MATRIX.md` (forward + backward + coverage-summary tables, appended after the Performance section's closing note). Root matrix is ~550KB / 4000+ lines -- too large to Read whole; grep for anchors and append after the trailing `*Note:` paragraph.

**Why (key accuracy issue, flag on every ADM isolation story):** US-ADM-001 AC-6 + FR-6 specify PostgreSQL RLS + the `app.current_tenant_id` session variable as the isolation mechanism. This codebase does NOT use Postgres RLS -- it enforces tenant isolation via EF Core global query filters (read, `AppDbContext.OnModelCreating`) + `TenantInterceptor` (write stamping). RLS is a deferred platform extension point. The orchestrator explicitly instructs framing isolation tests against the EF query-filter mechanism, NOT RLS.

**How to apply:** Write all ADM isolation TCs (and any AC-6-style "RLS active" criterion) against EF query filters + TenantInterceptor; document the story's raw-SQL RLS-verification hint as CONDITIONAL/deferred; assert cross-tenant ID-injection returns **404 not 403** (existence not disclosed) per the story Test Hints. Note RLS as the future hardening layer. This is a genuine story/implementation mismatch -- report it to the caller (the story should be reworded), do not silently "test RLS". Same pattern as the Payroll AC-5/FR-8 "RLS at the query level" deferrals.

Other ADM deferrals to write as CONDITIONAL, not gaps: FR-7 Redis tenant-config cache `t:{tenantId}:config` (assert tenant-keyed; if no cache layer wired, assert always-tenant-filtered + flag the Redis key as target); welcome-email DELIVERY (FR-4) asserted against a test SMTP sink, the dispatch/enqueue is the real assertion; NFR-1 <60s/<5min needs a perf-representative environment.
